# YouthLink RAG 서버 설계 정리

> RAG Technique 담당 기준. 백엔드는 이 저장소의 FastAPI 서버 하나로, 공개 API(프론트), 채팅 저장, RAG 파이프라인을 맡는다 (8주차에 Spring 제외, 15절).
> 최종 수정: 2026-10-23 (8주차)

---

## 0. 확정된 방향

| 항목 | 결정 |
|---|---|
| 구조 | **워크플로우형**. LLM은 해석을 맡고, 처리 방식 결정은 코드가 한다. 질문 이해는 **LLM 기반 쿼리 라우팅**(intent 분류 → 코드가 핸들러 선택)과 **질문 재작성**으로 구성 |
| 구현 | **FastAPI로 직접 구현**. 부품 라이브러리는 적극 활용, LangChain은 로컬 실험용 |
| DB | **PostgreSQL + pgvector**. 정책 데이터와 벡터 검색을 같은 DB에서 처리 (SQL JOIN으로 필터링 가능) |
| 백엔드 | **FastAPI 서버 하나**가 공개 API(프론트), 채팅 저장·조회, RAG를 맡음. 로그인 없이 익명 `X-Client-Id`로 사용자 구분. Spring은 두지 않음 (8주차 결정, 15절) |
| 핵심 원칙 | **파이프라인은 순수 함수**, 저장은 별도 계층. 저장 위치가 바뀌어도 파이프라인과 테스트는 유지 |
| 품질의 핵심 | Advanced 기법 조합보다 **질문 이해와 처리 방식 결정** |
| 구조 원칙 | 디렉터리 구조는 유지하고, 새 기능은 **파일과 폴더 추가**로 확장. 코드 수정은 허용 |

## 1. 먼저 합의해야 할 것

### 1-1. ETL과의 데이터 계약

**확정** (ETL `db/schema.sql`, `db/migrations/` 기준)
- **임베딩 모델과 차원**: `text-embedding-3-small`, 1536차원. 질문도 같은 모델로 임베딩 (`policy_chunk.embedding_model`로 확인)
- **거리 기준**: 코사인 → pgvector `<=>` 연산자, 점수는 `1 - 거리`
- **벡터 인덱스**: HNSW (`vector_cosine_ops`), `WHERE embedding IS NOT NULL` 조건부 인덱스 → 검색 쿼리에도 `embedding IS NOT NULL` 조건 필요

- **지역 코드**: `policy_region.region_code`는 온통청년 API `zipCd` 원본(법정 시군구 코드 5자리, 예: `11680` 서울특별시 강남구). 시도 단위 코드는 없고, 전국 정책은 전국 시군구 코드를 모두 나열
- **지역 코드 해석**: ETL이 VWorld 현재 시군구(`region`), 옛 코드 → 현재 코드 매핑(`region_code_mapping`, 1:N), 정책별 해석 View(`v_policy_region_resolved`)를 적재. RAG는 View를 사용
- **지역 코드 보정·범위 판정** (ETL 007, [ETL #3](https://github.com/inha-youthlink/youthlink-data-pipeline/issues/3) 닫힘): 인천 영종구·서해구 누락을 View에서 `INFERRED`로 보정. 정책 단위 `v_policy_region_scope`, 정책·시도 단위 `v_policy_sido_scope`로 "전국", "시도 전체" 판정 제공
- **청크 구조** (ETL `docs/rag-chunk-strategy.md`, 생성기 `policy-v1`, 6주차 확인)
  - 정책당 **최대 4청크**, 종류별 최대 1개 (`UNIQUE (policy_no, chunk_type)`). 전체 약 12,867개, 정책당 평균 3.9개

    | `chunk_index` | `chunk_type` | 내용 |
    |---|---|---|
    | 0 | `SUMMARY` | 정책 설명(`description`), 키워드, 분류, 기관. 항상 생성 |
    | 1 | `ELIGIBILITY` | 적용 지역(압축된 이름), 연령, 혼인·소득, 전공·직업·학력·특화, 추가 자격, 참여 제외 대상 |
    | 2 | `SUPPORT` | 지원 내용(`support_content`), 규모, 선착순, 제공 방식, 사업 기간 |
    | 3 | `APPLICATION` | 신청 기간, 신청 방법, 심사 방법, 제출 서류 (URL 제외) |

  - LLM을 쓰지 않는 규칙 기반 생성. 각 필드를 `라벨: 원문`으로 이어 붙이고, 코드는 이름으로 변환. 같은 DB 상태면 같은 결과
  - 모든 청크에 `정책명` 포함. 필드는 청크끼리 겹치지 않음
  - 청크에 쓰이지 않는 `policy` 컬럼은 관리용(기관 코드, 담당자 이름, 수집 시각, `raw_data`)뿐
  - 갱신: `content_hash`가 바뀐 청크만 재생성·재임베딩. 임베딩 전 청크는 `embedding`, `embedding_model`이 `NULL`
  - RAG 쪽 대응은 10-5

### 1-2. 자격 조건 저장 규칙
- 나이: `min_age`, `max_age`, `age_limit_yn`
- 소득: `income_condition_code`, `min_income`, `max_income`, `income_etc`
- 지역: `policy_region` (법정 시군구 코드)
- 혼인, 전공, 직업, 학력, 특화 대상: `marriage_status_code`, `policy_eligibility_code`
- 구조화 어려운 조건: `additional_qualification`, `participation_exclusion`
- **"제한 없음"과 "정보 없음"의 표현 규칙**
  - 확인됨: 컬럼의 `NULL`은 정보 부재나 변환 실패일 수 있으므로 "제한 없음"으로 해석하지 않음
  - 확인됨: "제한없음"은 명시적인 코드로 존재 (`common_code`의 `0011009` 전공, `0013010` 취업, `0049010` 학력, `0014010` 특화, `0055003` 혼인). 코드 존재 여부만으로 자격을 판단하지 않음
  - 확인됨: 온통청년 API에 빈 `zipCd`는 없음 (10-09 기준 0건). 전국 정책은 전국 시군구 코드를 모두 나열. 행이 없는 정책이 생기면 위 `NULL` 원칙과 같이 전국으로 보지 않음
  - 이 규칙이 모호하면 **전공무관 정책 누락 문제**가 그대로 재현됨

### 1-3. 테이블 소유권

| 테이블 | 쓰기 | 읽기 |
|---|---|---|
| `policy`, `policy_region`, `policy_eligibility_code`, `common_code`, `policy_chunk`, `region`, `region_code_mapping` | ETL | RAG |
| `chat_room`, `chat_profile`, `chat_message`, `message_policy_ref`, `chat_current_policy` | **RAG** | **RAG** |

어느 시점이든 **한 테이블에 쓰는 서버는 하나**.

- 공개 API에서 새로 필요한 서비스 테이블(스크랩, 세션 카테고리, `clientMessageId` 등)도 같은 규칙: 데이터는 백엔드(이 저장소)가 쓰고, DDL은 ETL 저장소에서 관리

**채팅 테이블 DDL** (6주차 결정): DDL과 마이그레이션은 ETL 저장소(`db/schema.sql`, `db/migrations/`)에서 관리하고, 변경은 RAG가 ETL 저장소에 이슈·PR로 진행한다. 데이터는 RAG가 쓴다.
- 스키마를 한곳(ETL 저장소)에서 보고, 한 DB에 마이그레이션 방식을 하나만 유지한다
- "한 테이블에 쓰는 서버는 하나"는 데이터 쓰기 기준이라 그대로 지켜진다

## 2. 시스템 구성

3개 서버로 운영한다 (8주차에 Spring 제외, 15절).

| 서버 | 역할 |
|---|---|
| **ETL 서버** | 온통청년 API 수집, 정책 테이블 적재, 청크·임베딩 생성. 서비스 테이블 DDL 관리 |
| **백엔드** (이 저장소, FastAPI) | 공개 API(프론트), 채팅 저장·조회, 질문 이해·검색·답변 생성 |
| **RAG 평가 서버** | `/internal/pipeline`을 호출해 RAG·LLM 성능 평가 |

```
[프론트 (Vercel)] ── /api/* (rewrite) ──→ [백엔드: 공개 API]
                                             ├ 서비스 (세션 소유 확인, 멱등 처리, 코드 변환)
                                             ├ 저장소 (chat_*, 스크랩)
                                             └ RAG 파이프라인 (DB 쓰기 없음)
[RAG 평가 서버] ── /internal/pipeline ──→ [백엔드: RAG 파이프라인]   (외부 비공개)
[ETL 서버] ── 정책·청크 적재 ──→ [PostgreSQL + pgvector] ←── 읽기·쓰기 ── [백엔드]
```

- 서버를 나누지 않고 한 서비스 안에서 계층(공개 API / 내부 API / 서비스 / RAG 파이프라인)으로 책임을 나눈다
- RAG 파이프라인은 DB에 쓰지 않고 입출력만 갖는 경계를 유지한다. 나중에 분리할 이유(팀 분리, AI 서버만 따로 확장)가 생기면 이 경계에서 떼어 낸다

### 3-4. 구현 포인트
- `config.py`: `pydantic-settings`로 `.env` → 타입 검증된 설정. `@lru_cache`로 한 번만 로드. 우선순위는 환경 변수 > `.env` > 기본값
  - 필수 값(`OPENAI_API_KEY`, `DATABASE_URL`)은 기본값 없음 → 빠지면 서버 시작 시 에러
  - 비밀 값은 `SecretStr`로 로그 출력 시 가림
  - `env_ignore_empty=True`: `.env`의 빈 값은 기본값 사용. `.env.example`은 필수/선택 섹션으로 나누고 선택 값에 기본값 주석
  - `.env` 변경 후에는 서버 재시작 필요 (`--reload`는 `.py` 변경만 감지)
- lifespan에서 OpenAI 클라이언트, DB 엔진, 저장소, 검색기를 한 번 생성해 재사용. 잘못된 `RETRIEVER` 값은 서버 시작 시 실패
- 서버 시작 시에는 클라이언트·저장소 객체만 만들고 DB 조회는 하지 않음 (DB 상태와 무관하게 서버 기동). 공통 코드 같은 참조 데이터도 요청 시 조회
- 파이프라인 의존성(`PipelineDeps`: 설정, LLM, 검색기, 저장소)은 `Depends`로 주입 → 테스트에서 `dependency_overrides`로 교체
- 모든 엔드포인트와 LLM 호출은 async, 병렬 호출은 `asyncio.gather`
- OpenAI 호출에 타임아웃과 재시도
- 스트리밍은 `StreamingResponse`(SSE), 상태와 출처는 마지막 이벤트로
- `/internal/*`은 외부에 노출하지 않음 (내부 네트워크 또는 API 키)
- `/health`는 서버 생존 확인만. 외부 서비스(OpenAI) 확인은 넣지 않음

## 4. API 설계

### 4-1. 내부용 (계속 유지)
```
POST /internal/pipeline   PipelineInput → PipelineOutput (저장 없음)
```
- 호출: 직접 테스트, RAG 평가 서버. 외부(프론트)에는 공개하지 않음
- 응답 형식은 필드 추가만 자유롭게
- `?debug=true` (6주차): trace에 `contexts`(LLM에 넘긴 정책별 근거 블록)와 `retrieved_chunks`(청크 본문 포함)를 추가. 기본 요청은 API 계층의 허용 목록으로 가벼운 키만 반환 (`latency_ms`, `tokens`, `chat_model`, `retriever`, `top_k`, `prompt_version`, `embedding_model`). RAG 평가 서버는 항상 debug로 호출

### 4-2. 채팅 API (6주차, 공개 API로 대체 예정)
```
POST /api/rooms                              채팅방 생성 (user_id, profile) → 201, room_id
GET  /api/rooms?user_id=...                  사용자의 채팅방 목록 (최근 대화 순)
GET  /api/rooms/{room_id}/messages?user_id=  대화 기록 조회
POST /api/rooms/{room_id}/messages           질문 전송 (user_id, question)
```
질문 전송 응답 (6주차 확정):
```json
{
  "message_id": 14,
  "answer": "...",
  "policies": [
    { "policy_no": "...", "policy_name": "...", "application_start_date": "2026-10-01",
      "application_end_date": "2026-10-31", "application_url": "...", "score": 0.82 }
  ]
}
```
대화 기록 조회 응답:
```json
{
  "messages": [
    { "message_id": 13, "role": "user", "content": "...", "created_at": "...", "policies": [] },
    { "message_id": 14, "role": "assistant", "content": "...", "created_at": "...", "policies": [ ... ] }
  ]
}
```
- `policies`는 `/internal/pipeline`과 같은 `PolicyItem`. 배열 순서가 카드 순서이고 `message_policy_ref.display_order`(1부터)로 저장된다
- 기록 조회의 `policies`는 저장된 순서로 복원하되, 이름·날짜·URL은 조회 시점의 `policy` 값이다
- 프로필은 채팅방 생성 때만 받는다 (5-3). trace와 `metadata`는 응답에 넣지 않는다
- 오류: 없는 채팅방·다른 사용자의 채팅방 404 (구분하지 않음), 요청 검증 422, OpenAI·DB 실패 503
- Swagger와 테스트 스크립트로 확인하는 용도로 만들었고, 4-3 공개 API의 세션·채팅으로 대체한다 (두 벌을 유지하지 않음)

### 4-3. 공개 API (프론트 계약 기준, 8주차 결정)
- 기준: 프론트 저장소의 `spec/api-contract.md` (v0.3, 합의 전). 경로·enum·오류 형식은 계약을 따르고, 백엔드가 DB 코드로 변환한다 (지역 `SEOUL` → 시군구 코드, 학력 등 enum → `common_code`, 연소득 만 원 → 원)
- 사용자 식별: 로그인 없음. `X-Client-Id`(UUID) 헤더로 세션·스크랩 소유자를 구분하고, 남의 세션은 404

| 엔드포인트 | 내용 |
|---|---|
| `POST/GET /api/sessions`, `GET /api/sessions/{id}`, `GET /api/sessions/{id}/messages` | 세션(카테고리 + 프로필 8항목), 목록, 단건, 메시지 이력 (카드 복원) |
| `POST /api/sessions/{id}/chat` | 채팅 SSE: `token` / `policies` / `done` / `error`, 15초 `:ping`. `clientMessageId` 멱등 처리, 연결이 끊기면 생성 취소 |
| `POST /api/sessions/{id}/summary`, `GET /api/sessions/{id}/recommendations` | 대화 요약 (LLM), 추천 정책 (1차 필터링 재사용) |
| `GET /api/policies`, `GET /api/policies/{id}` | 정책 검색 (키워드·카테고리·지역, 페이지), 상세 |
| `POST /api/sessions/{id}/guides` | 맞춤 신청 가이드 PDF (S3 presigned URL, 10분 이하 만료). 중간 시연은 mock 허용 |
| `GET/POST/DELETE /api/scraps` | 스크랩 (멱등) |

- 공통: 오류 형식 `{code, message, details}`, 요청 제한(IP + `X-Client-Id`, 특히 LLM을 부르는 API, `429`), `GET /sessions`에 `Cache-Control: no-store`
- SSE의 `policies`는 답변 첫 줄(`[소개: …]`)로 카드가 정해지는 즉시 본문보다 먼저 보낸다 (12절, 응답 속도)
- 프론트와 협의할 것(카드 신청 상태, 카테고리 대응, 정책 지역 표시, 세션 제목, 상세 필드 등): [weekly/week08.md](weekly/week08.md) 7절

## 5. 채팅 데이터 모델 (ETL 담당 ERD 기준)

### 5-1. 현재 ERD (ETL 마이그레이션 008 반영, 6주차)
```
chat_room            room_id(UUID), user_id, title, created_at, updated_at
                     인덱스 (user_id, updated_at DESC)
chat_profile         room_id(PK,FK), age, gender, region_code, marriage_status_code,
                     annual_income, major_code, job_code, school_code,
                     special_target_code, extra_profile(JSONB), updated_at
chat_message         message_id(BIGINT), room_id(FK), role, content, metadata(JSONB), created_at
message_policy_ref   message_id(PK,FK), policy_no(PK,FK), relevance_score, display_order
                     UNIQUE (message_id, display_order), display_order >= 1
chat_current_policy  room_id(PK,FK), policy_no(PK,FK), display_order    ← 7주차부터 갱신
```
- `message_policy_ref`가 답변에 보여준 정책과 순서를 저장 → 대화 상태의 "직전에 보여준 정책 목록"으로 사용
- `chat_message.metadata`: 질문은 사용자가 보낸 것(버튼 입력 등, 6주차는 `{}`), 답변은 만든 과정(가벼운 trace 키 + `retrieved_chunks`의 `policy_no`·`chunk_type`·`chunk_index`·`score`). 근거 원문은 저장하지 않음
- 한 턴(질문, 답변, 정책, `updated_at`)은 답변까지 성공한 뒤 한 트랜잭션으로 저장. 같은 턴의 메시지는 `created_at`이 같아 순서는 `message_id`로 보장

### 5-2. 추가 확인 필요
- 마감 정책을 삭제하는지 보관하는지 (`message_policy_ref`가 `policy`를 FK로 참조). 6주차 확인: ETL은 정책을 삭제하지 않음 (사라진 정책 비활성화도 미구현). 삭제하면 과거 대화의 정책 연결도 CASCADE로 사라지므로 비활성화가 유리 (ETL PR #5에 전달)
- 첨부파일 출처 청크의 원본 파일명/URL 저장 여부 (답변 출처 표시용)

### 5-3. 운영 원칙
- 채팅방 ID는 UUID, 요청마다 사용자-채팅방 소유 관계 확인
- 채팅방 소유자 식별값: 프론트가 브라우저마다 만드는 익명 UUID(`X-Client-Id`)를 `user_id`에 저장한다 (8주차)
  - 로그인·인증은 없고, 요청의 값과 채팅방의 값만 비교한다. 다르면 404
  - 사용자 테이블이 없어 FK는 두지 않는다. `X-Client-Id`는 누구나 새로 만들 수 있어 요청 제한이 필요하다 (4-3)
  - `chat_room.user_id`는 처음부터 `NOT NULL` + 인덱스 (나중에 추가하면 기존 채팅방 보정과 API 명세 변경 필요)
- 채팅방 프로필 (6주차 결정)
  - 채팅방을 만들 때 한 번 받고 **이후 수정하지 않는다**. 질문 전송 요청은 프로필을 받지 않고, RAG가 `chat_profile`에서 읽는다
  - 이유: 채팅방 하나의 모든 답변이 같은 조건 기준이 된다. 중간에 바꾸면 이전 답변(자격 안내 등)이 현재 프로필과 어긋난 채 기록에 남는다. 조건이 바뀌면 사실상 다른 상담이라 새 채팅방이 자연스럽다
  - 프로필은 세션을 만들 때만 받고 수정하지 않는다. 다른 지역·나이는 질문에 말하면 된다 (10-2 "질문 > 프로필" 원칙). 조건이 바뀌면 새 세션
- 개인정보 보관 기간 정의 (회원 탈퇴 시 삭제, 세션 사용자의 오래된 채팅방 정리 등)

## 6. 요청 하나의 처리 흐름

```
[chat_service]
  1. 사용자-채팅방 소유 확인
  2. 프로필, 최근 3~5턴, 현재 정책 목록, 직전에 보여준 정책 조회
  3. PipelineInput 구성 → run_pipeline()
  4. 메시지, metadata, message_policy_ref, 상태 저장
  5. 응답 반환

[run_pipeline]
  ① 질문 분석 (LLM 1회, 구조화 출력) — action이 있으면 생략
  ② 출력 검증
  ③ intent별 핸들러 실행
  ④ 관련성 판정
  ⑤ 답변 생성
  ⑥ (선택) 답변 검증
  ⑦ 갱신된 상태와 trace 반환
```

## 7. 대화 상태

| 항목 | 의미 | 용도 |
|---|---|---|
| **직전에 보여준 정책 목록** | 직전 답변에 등장한 정책들 (`message_policy_ref`). 순서는 정책 카드(`policies`) 순서, `display_order` 1부터 | "두 번째 거", "그중에 월세" 등 **목록 안 지목** |
| **현재 정책 목록** | 지금 대화가 집중하는 정책 (보통 하나, 복합 질문·비교면 여러 개). `chat_current_policy` | 정책 이름 없는 **후속 질문**의 기본 대상 |

- **설정**: 상세보기 클릭, 특정 정책 지목, 답변이 정책 하나를 자세히 다룬 경우
- **교체**: 다른 정책을 명확히 지목
- **초기화**: 화제 전환 (`is_new_topic`)

| 턴 | 대화 | 보여준 정책 | 현재 정책 |
|---|---|---|---|
| 1 | "서울 주거 지원 정책 뭐 있어?" → 3개 | [월세, 전세대출, 임대주택] | 없음 |
| 2 | "두 번째 거 자세히" | [전세대출] | **전세대출** |
| 3 | "소득 기준은?" | [전세대출] | 전세대출 |
| 4 | "신청 서류는?" | [전세대출] | 전세대출 |
| 5 | "월세 지원이랑 비교하면?" | [전세대출, 월세] | 전세대출 |
| 6 | "청년 취업 정책도 알려줘" | [취업A, 취업B] | **초기화** |

- LLM에는 최근 3~5턴과 상태만 전달, 긴 이전 답변은 앞부분만
- 현재 정책을 목록으로 둔 이유: "A 서류 뭐야? B도 받을 수 있어?"처럼 한 질문이 여러 정책을 다루면, 하나만 남길 경우 다음 후속 질문에서 나머지가 빠진다 (6주차 결정)

## 8. 질문 이해: 쿼리 라우팅, 질문 재작성 (가장 중요한 단계)

LLM이 질문을 분석해 intent를 분류하고(**LLM 기반 쿼리 라우팅**), 대화 맥락을 반영해 질문을 다시 쓰고 지시 대상을 찾는다(**질문 재작성**, **정책 지목**). LLM은 경로를 직접 고르지 않고 구조화된 분석 결과만 출력하며, 결과를 검증한 뒤 핸들러를 고르는 것은 코드가 한다.

### 8-1. 역할 분담

| LLM이 하는 일 | 내가 설계하는 것 |
|---|---|
| 의도 분류 | 의도 범주와 출력 스키마 |
| "그 정책"이 가리키는 정책 지목 | LLM에 넣을 맥락 (대화, 후보 목록, 프로필) |
| 대화 맥락 반영 질문 재작성 | 프롬프트와 few-shot 예시 |
| 새로 언급된 정보 추출 | 결과 이후의 규칙, 검증, 대체 경로 |

### 8-2. LLM 없이 확정되는 입력
- 정책 카드 "상세보기" → 현재 정책 설정
- "신청 가이드 PDF", "추천 정책" 버튼 → `action`
- 채팅방 생성 시 프로필

### 8-3. 출력 검증
- 후보에 없는 정책 ID → 버리고 되묻기
- 애매한 분류 → `unclear` 또는 기본 RAG 경로 (`default_rag`)
- 스키마 오류 → 재시도 또는 기본값

### 8-4. 규칙

| 상황 | 규칙 |
|---|---|
| 화제 전환 | 현재 정책 초기화 또는 교체 |
| 여러 정책 중 "그 정책" | 현재 정책 우선, 없으면 되묻기 |
| 현재 정책이 여러 개일 때 이름 없는 후속 질문 | 정할 것 (전부 답변 / 되묻기, 최대 개수) |
| 프로필과 대화 충돌 | 이번 답변은 대화 우선, 계속 반영하려면 새 채팅방 안내 (채팅방 프로필은 수정 불가, 5-3) |
| 저장된 정책 마감/수정 | 조회 시 최신 상태 재확인 |

### 8-5. 복합 질문 처리 (정할 것, 7주차)
한 질문에 여러 의도가 섞인 경우 (예: "A 신청 서류 뭐야? 그리고 나 B도 받을 수 있어?")

- 질문 분석 출력은 처음부터 **하위 질문 목록**으로 둔다 (단일 의도는 길이 1). 나중에 단일 → 목록으로 바꾸면 프롬프트, 검증, 핸들러 선택, trace를 모두 고쳐야 함
- 핸들러는 **근거만 반환**하고 답변 생성은 마지막에 한 번. 핸들러마다 답변을 만들면 결합이 어렵고 LLM 호출이 늘어남
- 7주차 실행 범위: 하위 질문 1개만 정상 경로, 2개 이상은 `default_rag`. 여러 하위 질문 실행·결합은 비교 핸들러(8주차)와 함께

**정할 것**
- 하위 질문 최대 개수 (예: 3)
- 답변 결합 형식 (12-1 유형별 답변 명세와 함께)
- 현재 정책 목록 갱신 규칙 (하위 질문들의 대상을 모두 넣을지)
- trace에 하위 질문별 근거 구분

## 9. 핸들러

질문 분석이 모든 질문에 공통으로 **질문 재작성**("그 정책 서류 뭐야?" → "청년 월세 지원 제출 서류")과 **정책 지목**("두 번째 거" → 직전에 보여준 목록의 2번째 정책)을 먼저 수행한다. 따라서 후속 질문은 별도 유형이 아니라, 재작성된 뒤 아래 유형 중 하나로 분류된다.

**구조 (8주차 결정)**: 라우터(`runner`)가 분석 결과로 핸들러 **하나**를 고르고, 핸들러는 정해진 조립법대로 부품(검색, 후보 선택, 근거 만들기)을 불러 **근거와 카드 후보만** 모은다. 답변 생성은 공통 함수 하나가 핸들러가 넘긴 답변 종류로 **프롬프트 조각**(공통 + 목록·상세·짧은 답변·되묻기)을 조립해 한 번 호출한다. 핸들러끼리는 서로 호출하지 않는다.

**원칙**: 근거를 모으는 방법이 다를 때만 핸들러를 나눈다. 확실하면 전용 핸들러, 판단이 안 서면 되묻기.

| 핸들러 | 받는 질문 | 근거 | 답변 조각 |
|---|---|---|---|
| 검색 | 목록·찾기. 자격 확인·비교·복합 질문(전용 처리 전까지). 분석 실패 (분석 조건 없이) | 1차 필터 → 벡터 검색 → 후보 5개 → 청크 전체 | 추천 (최대 3개) |
| 상세 | `policy_detail` + 지목한 정책이 확인됨 | 지목한 정책 (`policy_ids`, 검색 없음) | 상세 |
| 짧은 답변 | 인사, 서비스 질문, 분명한 범위 밖 | 없음 | 짧은 답변 |
| **되묻기 (기본)** | `unclear`, 판단이 안 서는 모든 경우 | 없음 | 되묻기 (현재 정책이나 질문 예시 + 범위 안내) |
| 자격 확인 (시간이 되면) | `eligibility` + 지목한 정책 | 상세 + 조건별 판정 (1차 필터링과 같은 판정 함수) | 자격 확인 |

- 되묻기를 기본으로 두는 이유: 기본까지 오는 질문은 대부분 "정책 관련인데 애매한 질문"이다. 짧은 답변이 받으면 정책 질문에 범위 밖이라고 답해 대화가 끊긴다
- 되묻기로 보내지 않는 것: 분석 실패(시스템 실패), 분명하지만 전용 처리가 없는 질문 → 검색
- 두지 않는 것: 정책 목록 SQL 핸들러(목록 질문도 주제가 자유 표현이라 "필터 → 의미 검색"), RAG 없는 범용 LLM 핸들러(일반 지식으로 지어낼 위험)
- 나중: 개수 지정("5개 알려줘")은 검색 핸들러의 매개변수, "모두 알려줘"는 목록 핸들러, 비교 핸들러, 복합 질문은 하위 질문마다 핸들러를 실행하고 근거를 합쳐 생성 1회
- 결정 과정과 버린 안: [weekly/week08.md](weekly/week08.md) 3절

근거: [5주차 기본 RAG 동작 확인](weekly/results/week05_testdata_result.md). 후속 질문의 "두 번째 거"를 임의로 해석(F2), 목록 질문에서 벡터 검색이 정책을 누락(L1), 범위 밖·판단 불가는 프롬프트만으로 대부분 처리됨

**핸들러 추가 원칙 (6주차 결정)**

모든 경우를 미리 처리하려 하지 않는다. 기본 경로(`default_rag` + 질문 분석)로 시작하고, 실패 사례를 보고 필요한 곳만 분리한다.

| | 기본 경로로 잘 됨 | 기본 경로로 안 됨 |
|---|---|---|
| **자주 나옴** | 분리 안 함 | 먼저 분리 |
| **드묾** | 분리 안 함 | 되묻기·안내로 끝내고, 쌓이면 검토 |

- 실패 원인에 따라 고칠 곳이 다르다. 핸들러 추가는 그중 하나다

| 실패 원인 | 고칠 곳 |
|---|---|
| 질문을 잘못 이해함 | 질문 분석 프롬프트, few-shot |
| 정책을 잘못 찾음 | 검색 범위(`policy_ids`), 1차 필터링 |
| 답변 형식이 이상함 | 답변 프롬프트, 유형별 답변 명세 (12-1) |
| 처리 방식 자체가 달라야 함 (SQL 조회, 코드 판정) | **핸들러 추가** |

- 진행: 기본 경로로 시작 → 평가 서버, trace, `metadata`로 실패 사례 수집 → 원인 분류 → 해당 위치 수정 → 재평가
- 대상 정책이 정해지면 `default_rag`도 그 정책들로 검색을 제한한다 (`policy_ids`). 상세, 가벼운 비교·복합 질문은 별도 핸들러 없이 이 방식으로 먼저 처리한다
- 핸들러를 나중에 추가하기 쉽도록 세 가지는 처음부터 지킨다: 질문 분석 출력은 목록 (8-5), 핸들러는 근거만 반환하고 답변 생성은 마지막에 한 번, 판단이 안 서면 되묻기

## 10. 검색

### 10-1. 기본
- pgvector 검색: 질문 임베딩과 `policy_chunk.embedding` 거리 정렬 후 top-k
- 1차 필터링 결과는 `policy_ids`로 받아 `WHERE policy_no = ANY(...)`로 제한. 같은 DB라 `policy_region` 등과 JOIN도 가능
- 검색 쿼리에는 `embedding_model = 설정값`과 `embedding IS NOT NULL` 조건을 항상 포함 (다른 모델 임베딩 혼입 방지, HNSW 조건부 인덱스 사용)
- **top-k는 청크 단위** → `policy_no`로 묶고 정책별 최고 점수를 대표값으로
  - 정책당 최대 4청크라 top-k가 추천 정책 수와 다르다 (`top_k=10`이면 정책 3~10개). 대응은 10-5
- Parent-child: 청크로 검색 후 `policy`에서 정책 정보 조회. 근거 구성 방식은 10-5

### 10-2. 프로필 기반 1차 필터링

**문제 인식**
- 후보가 적어지는 것 자체는 큰 문제가 아님. 벡터 검색은 후보 수와 관계없이 동작하고, 후보가 적으면 관련 없는 정책이 섞일 여지도 줄어듦
- 진짜 위험은 **잘못된 제외**. 정책 데이터에는 `NULL`(정보 없음), "제한없음" 코드, 지역 행 없음 등 해석이 애매한 값이 많아, 프로필이 세부적일수록 받을 수 있는 정책이 조용히 사라질 가능성이 커짐 (전공무관 정책 누락 문제)

**원칙: 확실히 불충족인 정책만 제외**

자격 판정과 같은 3단계 판정을 필터링에도 적용한다.

| 판정 | 처리 | 예시 |
|---|---|---|
| **불충족** (확실함) | 제외 | `max_age=34`인데 사용자가 40세 |
| **판단 불가** | 남김 + 답변에 "확인 필요" 표시 | 나이 컬럼 `NULL`, 지역 행 없음 |
| **충족** | 남김 | "제한없음" 코드, 조건 범위 안 |

**조건별 강도 (8주차 결정)**: 질문에 명시된 것 > 프로필 > 없음. 프로필과 어긋나면 숨기지 않고 알린다 (예: 서울 사용자가 "인천 창업 지원"을 물으면 인천으로 찾고, 거주 조건이 다를 수 있다고 안내)

| 조건 | 질문에 명시 | 질문에 없음 | 강도 |
|---|---|---|---|
| 지역 | 질문 지역 + 전국 | 프로필 지역 + 전국 | 강제 |
| 나이 | 질문 나이 | 프로필 나이 | 강제 (나이 제한 없는 정책 포함) |
| 코드 조건 (취업 상태, 학력, 전공, 혼인, 특화 대상) | (나중) | 프로필 코드 | 강제. 프로필 코드가 있고 정책 목록이 "제한없음"·"기타"가 아닌데 목록에 없을 때만 제외 |
| 소득 | (나중) | 프로필 연소득 | 강제. 숫자 **상한**을 확실히 넘을 때만 제외 (하한은 부부 합산일 수 있어 쓰지 않음) |
| 마감 여부 | "지금 신청 가능한" → 제외 / "마감된 것도" → 포함 | 정렬만 | 명시되면 강제 |
| 분야 | "주거 정책" | — | 참고만 (정책 분류가 엇갈림: 창업자 월세 지원이 일자리 분류) |

- **강제 필터는 결과가 적어도 풀지 않는다.** 조건에 따라 동작이 바뀌면 예측하기 어렵고 자격 없는 정책이 카드로 나온다. 결과가 없으면 한 문장으로 안내 ("프로필 조건에 맞는 관련 정책을 찾지 못했어요. 다른 표현으로 물어보시거나, 조건과 관계없이 찾아보고 싶으시면 말씀해 주세요")
- 분석이 실패하면 질문 조건을 모르므로 프로필 조건도 참고로 낮춘다
- **질문 유형별 적용**: 검색 핸들러만 적용. 지목한 정책 상세·비교는 적용하지 않고, 자격 확인은 거르지 않고 조건별 판정을 설명

**연결 방식**
- 필터링 결과는 정책 번호 목록으로 만들어 `Retriever.retrieve(query, policy_ids, k)`의 `policy_ids`로 전달. 검색 코드는 변경하지 않음
- 필터링 조회는 `policy_repository`에 추가 (DB 접근은 `repositories/`에서만)
- `policy_ids`가 적고 데이터가 많으면 HNSW 탐색 후 조건 적용 방식 때문에 결과가 k개보다 적을 수 있음 → pgvector 반복 탐색 옵션(`hnsw.iterative_scan`) 검토

**결정 전 확인**
- 실제 ETL 데이터로 대표 프로필 몇 개(예: 24세·서울·미취업·대학 재학)의 후보 수를 측정해 완화 기준을 정한다
- 1-2의 미정 규칙(`policy_region` 빈 행 의미, 복수 조건 AND/OR)이 정해져야 판정 기준을 확정할 수 있음
- 첫 조건은 신청 상태 (7주차, 10-4). 코드로 정확히 판정되고 ETL 답변을 기다리지 않아도 됨. 지역은 ETL 보정([ETL #3](https://github.com/inha-youthlink/youthlink-data-pipeline/issues/3)) 이후
- 지역 매칭: 정책은 법정 시군구 코드, 프로필은 공개 API 계약상 **시도 단위**(`SEOUL` 등, 8주차). 시도 코드 앞 2자리로 판단
  - 정책이 시도 전체(`11000`)면 그 시도의 시군구 사용자는 충족
  - 정책이 다른 시군구면 불충족
  - 사용자가 시도만 입력했고 정책이 시군구 단위면 판단 불가

### 10-4. 신청 상태 기반 우선순위 (정할 것)

**현재 (PR #25, #27)**: 검색된 정책을 신청 가능·상시 > 예정 > 정보 없음 > 마감 순으로 정렬해 후보 5개를 고른다. 정렬이 관련도를 보지 않아, 정책 이름을 직접 물은 마감·예정 정책이 밀리는 문제를 "확실한 1위 유지"(이름이 다른 다음 정책과 점수 차 0.05 이상, 같은 이름은 한 묶음)로 임시 처리했다. "관련도가 비슷할 때만 상태 우선" 같은 근본 규칙은 1차 필터링 뒤 **신청 상태 우선순위 PR**(8주차)에서 실제 데이터로 정한다.

**목표**: 신청 가능한 정책을 우선 보여주고, 관련 있는 신청 가능 정책이 없으면 마감 정책을 마감됐다고 안내한다.

**배경**
- 실제 데이터(10-09 기준 3,238건)의 약 68%가 마감이다 (마감 코드 931 + 기간이 끝난 특정기간 1,261). 신청 가능은 약 32% (특정기간 진행 중 276 + 상시 754), 신청 예정 15
- 검색 후 정렬만으로는 부족하다. top-k가 마감 정책으로 채워지면 관련 있는 신청 가능 정책은 후보에도 들어오지 못한다
- 현재는 프롬프트(`generate_v1`)가 답변 문장 안에서만 마감 정책을 뒤로 보낸다. 추천 목록(`policies`)은 검색 점수순이라 답변과 순서가 어긋날 수 있다
- 무조건 "신청 가능 → 상시 → 신청 예정 → 마감" 순으로 정렬할 수는 없다. 질문에 따라 마감 정책을 먼저 보여줘야 할 때가 있다 (특정 마감 정책을 지목한 경우 등)

**적용 위치**

| 단계 | 내용 | 방식 |
|---|---|---|
| 검색 | 신청 가능 정책을 후보에 우선 포함 | `policy_ids`로 상태 필터 → 부족하면 마감 포함 재검색 |
| 근거 순서 | LLM에 넘기는 `[근거]` 순서 | 코드로 정렬 |
| 추천 목록 | `policies` 순서 | 코드로 정렬 (근거 순서와 일치) |
| 답변 | 마감 안내 문구, 소개 순서 | 프롬프트 규칙 |

**역할 분담**

| 누가 | 하는 일 |
|---|---|
| 직접 설계·튜닝 | 상태 순서, 질문 유형별 적용 여부, 마감 정책을 보여줄 조건, 관련성 기준 |
| 질문 분석 (LLM) | 질문에 담긴 상태 관련 신호 추출 ("지금 신청 가능한 것만", "마감된 것도", 특정 정책 지목) |
| 코드 | 신호와 규칙으로 검색 범위와 순서 결정 |
| 답변 생성 (LLM) | 정해진 순서와 상태로 문장 작성 |

- 순서 결정을 LLM에 맡기지 않는 이유: 검색 단계의 결정이라 LLM이 근거를 보기 전에 정해야 함. 추천 목록·근거·답변 순서가 일치해야 함. 같은 질문에 같은 결과가 나와야 평가로 비교 가능. 신청 상태 계산을 코드로 옮긴 이유(LLM의 날짜 비교 오류)와 같음

**정할 것**
1. 상태 순서: 신청 가능(마감일 있음, 마감 임박 순 여부), 상시, 신청 예정, 정보 없음, 마감의 위치
2. 질문 유형별 적용 (10-2의 유형별 필터링과 같은 구조)

| 질문 유형 | 적용 (초안) |
|---|---|
| 정책 목록·탐색 | 상태 우선 적용 |
| 정책 상세 | 적용 안 함. 지목한 정책이 마감이면 마감이라고 답함 |
| 비교 | 적용 안 함 |
| 자격 확인 | 적용 안 함. 마감이면 함께 안내 |

3. "관련 있는 신청 가능 정책이 없다"의 기준 (벡터 검색은 항상 결과를 반환하므로 관련성 기준 필요, 11절과 연결)
4. 마감 정책의 범위: 마감 연도 제한 여부 (2025년 686건, 2026년 552건, 2024년 이전 23건). 매년 반복되는 정책은 "다시 열릴 수 있으니 공고 확인" 안내 여부
5. 질문 분석이 출력할 상태 관련 신호의 형태 (예: 신청 가능만 / 마감 포함 / 지정 없음)
6. trace 기록: 적용한 규칙을 남겨 평가 전후 비교 (`contexts` 순서가 바뀌면 Context Precision이 달라짐)

**확인 방법**
- 경우별 질문 세트와 기대 순서: 신청 가능 정책이 있는 경우, 마감 정책만 있는 경우, 마감 정책을 지목한 경우, 마감 포함을 요청한 경우
- debug 모드로 `contexts`, `policies` 순서 확인
- 가짜 데이터로는 "마감 68%" 상황이 재현되지 않으므로 실제 데이터로 다시 확인

**시점**: 7주차. 질문 분석 스키마 설계 → 이 규칙 확정 → 1차 필터링 순서로 진행한다
- 마감 코드 판정 수정이 먼저다 (6주차). 판정이 틀리면 우선순위도 틀린다
- 질문 분석 없이 `default_rag`에 상태순 정렬을 넣지 않는다. 질문 대상인 마감 정책이 뒤로 밀린다
- 1차 필터링(10-2)과 구현 방식(`policy_ids`)이 같아 함께 만든다. 신청 상태는 1차 필터링의 첫 조건이 된다

### 10-5. 섹션 청크(policy-v1)에 맞춘 검색과 근거 (7주차~)

ETL 청크가 정책당 최대 4개(요약·자격·지원·신청)로 나뉘어(1-1), RAG가 다음을 고려한다. 청킹 설계 자체는 바꾸지 않고 RAG가 청크를 쓰는 방식을 맞춘다.

**청크 구조의 장단점**
| 장점 | 단점 |
|---|---|
| 의미 단위 분할이라 질문 유형(자격·지원·신청)과 맞음. 세부 질문에 정확 | **검색 단위(청크) ≠ 답변 단위(정책)**: 필요한 섹션이 검색에 안 걸리면 답할 근거가 없음 |
| 청크마다 정책명이 있어 청크 하나로 정책을 알 수 있음 | 잘 맞는 정책 하나가 top-k를 여러 칸 차지해 정책 수가 줄어듦 (목록 질문에 불리). 모든 청크가 정책명을 공유해 같은 정책 청크가 함께 올라오기 쉬움 |
| `chunk_type`으로 유형별 검색 가능 | 많은 정책의 `ELIGIBILITY`가 비슷해("만 19~34세, 소득 무관, 전국") 일반적인 질문에 관련 없는 정책이 섞일 수 있음 |

**대응**
| 대응 | 내용 | 시점 |
|---|---|---|
| **근거는 정책 원본에서** | 청크는 어떤 정책을 찾을지(검색)에만 쓰고, LLM에 넘기는 근거는 `policy` 테이블 원본 필드로 구성 (parent document retrieval). 필요한 섹션이 검색에 안 걸려도 답할 수 있고, 청크 본문과 `policy` 필드가 겹치는 근거 중복(`APPLICATION` 청크와 `[신청 방법]`·`[제출 서류]`, `SUMMARY`의 기관과 `[담당 기관]`)도 사라짐 | 7주차 핸들러 확장 |
| 핸들러별 근거 범위 | 원본 전체를 넣으면 입력이 길어져 느려짐. 상세(정책 1개)는 전체, 목록(정책 여러 개)은 카드 정보 + 요약처럼 유형별로 정함 (12-1과 함께) | 7주차 |
| 정책 단위로 점수 모으기 | 청크를 넉넉히(예: 30~40개) 가져와 정책별로 묶고 상위 N개 정책 선택. C 방식의 "코드가 카드 수·순서 결정"(7주차)과 같은 단계 | 실제 데이터 측정 후 |
| 조건은 SQL, 의미는 벡터 | 나이·소득·지역은 1차 필터링·자격 판정(코드)으로. 벡터 검색은 "어떤 지원인가"에 집중 | 7~8주차 |
| 정책 이름은 키워드 검색 병행 | 고유 명칭은 벡터보다 BM25가 정확 (10-3) | 12~13주차 |

**측정할 것** (실제 데이터, 8주차 평가)
- 질문당 정책 수 (묶은 뒤), `top_k`에 따른 변화
- 필요한 섹션이 근거에 들어갔는지 (예: 소득 질문에 `ELIGIBILITY`)
- 필요하면 "정책당 청크 1개" 방식과 같은 질문 세트로 비교 (ETL 협의 필요)

## 11. "관련 정책 없음" 판정

- **벡터 검색은 항상 k개를 반환** → 별도 판정 필요
- 방법: 유사도 임계값, 리랭커 점수, LLM 관련성 판정 (리랭커 + LLM 조합이 흔함)
- RDB 필터 결과 0건이면 LLM 없이 바로 응답

| 상황 | 응답 |
|---|---|
| 조건에 맞는 정책 없음 | 없다고 안내 + **어떤 조건 때문인지** 설명 |
| 범위 밖 | 범위 안내 |
| 공고문에 정보 없음 | 명시되지 않았다고 안내 + 담당 부서 연락처 (`supervising_org_name` 등) |
| 프로필 부족 | 필요한 정보 되묻기 |

## 12. 답변 생성과 검증

- 입력: 재작성된 질문, 검색 근거(정책 번호, 청크 타입 포함), 프로필, 최근 3~5턴, **오늘 날짜**
- 근거는 청크 내용 + 정책 정보(정책명, 신청 기간, URL). 7주차부터 근거는 `policy` 원본 필드로 구성하고 청크는 검색에만 쓴다 (10-5)
- 신청 상태(상시 모집/신청 가능/신청 예정/마감/정보 없음)는 코드에서 계산해 전달 (LLM의 날짜 비교 오류 방지), 마감 정책은 답변에 명시
  - 상시(`0057002`)·마감(`0057003`)은 신청 기간 구분 코드로 판단. 두 코드의 정책은 신청 날짜가 없음 (10-09 API 기준 상시 754건, 마감 931건 모두)
  - 특정기간(`0057001`)은 신청 기간과 오늘 날짜를 비교 (마감일 경과 → 마감, 시작일 이전 → 신청 예정, 그 외 → 신청 가능). 날짜가 하나만 있으면 있는 날짜로 판단. 특정기간 코드는 기간이 끝나도 마감으로 갱신되지 않음 (1,553건 중 1,261건)
  - 코드로 판단할 수 없고 날짜도 없으면 정보 없음 (공고 확인 안내)
  - 날짜가 없으면 기간 없이 상태만 표시 (예: "마감")
- 프로필 코드 값은 `common_code`에서 요청마다 필요한 코드만 조회해 이름으로 변환 후 전달. 지역은 코드 사전이 적재되면 같은 방식으로 반영 (그 전까지 제외)
- 사실 정보는 **검색 근거에서만**. 이전 답변을 사실 근거로 재사용 금지
- 근거가 없으면 모른다고 답함
- 출처(정책명, `application_url`/`reference_url_*`) 표시
- intent별 프롬프트 분리, `prompts/`에 버전 파일로 관리
- 신청 가이드: `submission_documents`, `application_method`, 발급처 링크, 담당 기관
- 답변 검증(선택): 자격 확인 등 중요 유형에만, 실패 시 재생성 또는 안전 응답

### 12-1. 유형별 답변 명세 (정할 것)

**배경**
- `generate_v1`은 모든 질문을 한 경로로 처리하는 Naive RAG용 범용 프롬프트다. 목록·상세·자격·비교 규칙이 한 프롬프트에 섞여 질문 유형과 관계없이 적용된다 (예: "최대 5개 소개", "신청 방법과 링크를 끝에 안내")
- 핸들러를 나누면 유형마다 답변 목적이 달라진다. 답변 형식은 제품 결정이므로 프롬프트보다 먼저 정한다

**순서**
1. 유형별 답변 명세: 사용자에게 무엇을, 어떤 순서로 보여줄지
2. 프롬프트: 명세를 LLM 지시로 옮김
3. 확인 질문과 기대 답변: 명세대로 나오는지 확인

**유형마다 정할 항목**

| 항목 | 내용 |
|---|---|
| 목적 | 이 답변으로 사용자가 무엇을 할 수 있어야 하나 |
| 구조 | 결론과 목록의 순서 |
| 필수 포함 | 신청 상태, 링크, 담당 기관 등 |
| 정책 개수와 순서 | 몇 개까지, 어떤 순서로 (10-4와 연결) |
| 길이 | 대략적인 분량 |
| 근거가 없을 때 | "공고에 없음" 안내 방식 |
| 되묻기 조건 | 언제 되묻나 |
| 예시 답변 | 1~2개. 프롬프트 few-shot과 평가 기대 답변으로 재사용 |

**유형별로 생각해 볼 점**

| 유형 | 생각해 볼 점 |
|---|---|
| 정책 목록 | 정책별 "이름·상태·한 줄 설명" 형식 여부. 정책 카드가 따로 보이면 답변은 짧아도 됨 |
| 정책 상세 | 질문한 항목만 답할지, 신청 방법과 링크를 항상 붙일지 |
| 자격 확인 | 결론 → 조건별 충족·불충족·판단 불가 → 공고 확인 안내. 판정은 코드, LLM은 설명만 (9절) |
| 비교 | 항목별 나란히 비교. 표를 쓰려면 "표 금지" 규칙과 프론트 렌더링을 함께 정함 |
| 범위 밖 | LLM 없이 고정 문구 |
| 판단 불가 | 되묻기 문구, 선택지 제시 여부 |

**공통으로 정할 것**
- 답변 텍스트와 정책 카드(`policies`)의 관계: 카드에 이름·기간·링크가 보이면 답변에서 반복할 필요가 줄어듦 (프론트 화면 구성과 연결)
- 마크다운 범위: 현재는 목록(`-`)만 허용. 프론트 렌더링에 따라 결정
- 프롬프트 구성: 공통 규칙(근거 사용, 신청 상태, 존댓말, 식별자 금지)과 유형별 규칙을 나눌지, `prompt_version`을 유형별로 어떻게 기록할지

**시점**: 7주차 핸들러 확장 때, 각 핸들러를 구현하기 전에 해당 유형의 명세를 정한다 (정책 상세부터). 명세는 별도 문서(예: `docs/answer_spec.md`)로 두고, 예시 답변은 평가 담당자와 공유한다.

## 15. 백엔드 구성 결정: Spring 제외 (8주차)

**6주차 계획**: Spring이 로그인·사용자를 맡고 프론트 요청을 RAG의 채팅 API로 중계. 채팅 저장은 대화 상태가 RAG 규칙에 맞춰진 정보라 RAG에 둠.

**8주차 결정**: 로그인을 빼고 익명 `X-Client-Id`로 가기로 하면서 Spring을 두지 않는다. FastAPI 서버 하나가 공개 API까지 맡는다.

| 검토 | 판단 |
|---|---|
| 책임 분리 | 서버 단위 분리의 근거(팀 분리, 확장 방식·배포 주기 차이, 기존 Java 시스템, AI 서비스를 여러 곳에서 사용)가 없음. 한 서비스 안의 계층으로 충분 |
| Spring에 남는 일 | 로그인이 빠지면 대부분 RAG 채팅 API 중계. 같은 API를 두 번 만들고 유지 |
| 채팅 SSE | OpenAI → FastAPI → Spring → 프론트로 스트림을 두 번 이어야 하고, 연결 끊김 시 생성 취소를 두 서버에 걸쳐 전달해야 함. 한 서버면 바로 전달 |
| 정책 검색·추천 | Spring이 정책 테이블을 다시 읽으면 신청 상태 계산, 지역 해석, 1차 필터링을 다시 구현해야 함 |
| 일정 | 백엔드 1명. 공개 API 범위가 넓어(4-3) 한 서버로 해야 일정 안에 가능 |

**지켜야 할 것**
1. 파이프라인은 DB에 쓰지 않는다 (테스트와 평가를 위해 유지, 나중에 분리할 때의 경계)
2. 공개 API(`api/public/`)와 내부 API(`/internal/*`)를 나눈다. 내부 API는 외부에서 막는다 (배포 시 경로 차단 또는 API 키)
3. 사용자 식별은 `X-Client-Id`만 믿는다. 누구나 새로 만들 수 있으므로 요청 제한을 둔다
4. 공개 API 형식은 프론트 계약을 따르고, DB 코드와의 변환은 서비스 계층에서 한다 (파이프라인은 DB 코드 그대로)
5. 서비스 테이블 DDL은 ETL 저장소에서 관리 (1-3)

**나중에 고려할 것**
- 세션 사용자의 채팅방은 브라우저를 바꾸면 다시 열 수 없음. 오래된 세션 정리 규칙(예: 마지막 대화 후 N일)
- 로그인이 필요해지면 FastAPI에 추가. 서버 분리는 분리 근거가 생길 때 검토
