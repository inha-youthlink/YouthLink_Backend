# YouthLink 공개 API 계약

- 상태: **백엔드 검토안 v0.4 — 10-26 회의 전**
- 기준: 프론트 초안 `YouthLink_Front/spec/api-contract.md` **v0.3** (이 문서의 `R1`, `§2.3` 같은 번호는 프론트 초안의 번호)
- 범위: 브라우저(React) ↔ 백엔드(FastAPI) 공개 API `/api/*`. 평가 서버용 `/internal/*`은 다루지 않는다

> 이 문서는 프론트 초안에 대한 백엔드 답변이다. 앞쪽 1~3절에 **수락한 것, 백엔드 제안, 합의가 필요한 것**을 정리했다. 회의에서 합의된 항목은 아래 "계약 본문"에 옮겨 적고, 이 문서를 프론트·백엔드가 함께 보는 기준 문서로 쓴다(3절 H6).

### 1.2 조건을 붙여 수락
| 번호 | 내용 | 조건 |
|---|---|---|
| R1 | 서버 주소(Elastic IP, 포트) 9주차 1일(10-27) | **Spring이 아니라 FastAPI 서버 주소.** 로그인 없이 `X-Client-Id`로 가기로 하면서 Spring을 두지 않음. Vercel rewrites 대상만 바뀌고 프론트 코드 변경은 없음. 배포 전에는 로컬(`DEV_API_TARGET`)로 먼저 붙일 수 있게 함. Vercel 경유 SSE가 통과하지 못해 대안(sslip.io + TLS로 브라우저가 직접 연결, §6)으로 가면 백엔드에 CORS·HTTPS 설정을 추가함 |
| R4 | SSE 연결 유지 설정 | `SseEmitter`는 Spring 기능이라 FastAPI에서 **같은 조건**으로 맞춤: 연결 타임아웃 120초 이상, 15초 `:ping`, `Cache-Control: no-cache`, `X-Accel-Buffering: no` |
| R8 | 요청 빈도 제한 (IP + `X-Client-Id`, 특히 chat·summary·guides), 초과 시 `429 RATE_LIMITED` + `Retry-After` | **서버 배포와 함께 최소 제한**(IP당 분당 횟수)부터 넣고, `X-Client-Id` 단위·엔드포인트별 기준·`Retry-After`는 시연 전까지 다듬음. 서버가 공개 주소로 열리는 순간부터 LLM 비용 남용 위험이 생기기 때문. 평가 서버용 `/internal/*`은 별도로 막음 |
| R9 | 가이드 PDF presigned URL 만료 10분 이하, PDF에 넣을 프로필 항목 합의 | 수락. 다만 **PDF 생성은 이번 범위 뒤**로 미룸 (프론트 mock 유지). 동기·비동기(Q4)도 PDF 작업을 시작할 때 정함 |
| §1.4 | `502 RAG_UPSTREAM_ERROR` = "FastAPI 호출 실패" | 이제 FastAPI가 직접 응답하므로 의미를 **"LLM 호출 실패"**로 바꿔 그대로 씀 |
| §1.4 | 상태 코드 표 | 표에 없는 코드 추가: `413 PAYLOAD_TOO_LARGE`(본문 256KB 초과), `403 FORBIDDEN`(Vercel 출처 확인을 켰을 때 Vercel을 거치지 않은 요청), `404 NOT_FOUND`·`405 METHOD_NOT_ALLOWED`(없는 경로·메서드). 하루 LLM 상한에 걸려도 `429 RATE_LIMITED`이고 `message`로 구분("내일 다시 이용해 주세요") |
| §4.2 | 추천 정책 `GET /api/sessions/{id}/recommendations` (최대 10개, 신청 가능 우선) | 수락. 다만 기준이 "세션 프로필과 카테고리"에서 바뀜 (2절 B3) |

## 2. 백엔드 제안 (강력)

실제 정책 데이터와 지금까지의 RAG 평가 결과를 근거로, 꼭 바꾸고 싶은 것들이다.

### B1. 프로필 지역을 시군구까지 (§2.2, §2.3 `region`)
- **제안**: 시도를 고른 뒤 시군구 목록에서 고른다(필수). 목록 맨 위에 **"○○ 전체"** 선택지를 둔다
  - 서울·광역시는 **구**, 도는 **시·군** 단위 (예: 경기도 → 수원시. 수원시의 4개 구로 나누지 않음)
- **동작**: 정책을 "고른 시군구 + 그 시도 전체 + 전국" 대상만 남기고, **같은 시도의 다른 시군구 전용 정책은 뺀다.** "○○ 전체"를 고르면 지금처럼 시도 기준 (백엔드 구현됨, #36)
- **이유**: 시도 단위로만 거르면 다른 시군구 전용 정책이 섞여 나온다 (경기 수원 사용자에게 평택시·여주시 정책 카드, 서울 강남 사용자에게 성북구 정책). 정책 데이터가 서울은 구, 경기는 시·군 단위로 등록돼 있어 이 단위로 고르면 정확히 거를 수 있다 (경기도 지역 코드 47개 중 시 단위 정책은 그 시의 구 코드 전부로 등록, 구 하나만 대상인 정책은 경기 1건·서울 16건)
- 정책 검색(§4.3)의 `region` 필터도 같은 코드로 받고, 같은 범위(고른 지역 + 그 시도 전체 + 전국)를 보여 준다
- 프론트 영향: 프로필 입력 화면과 정책 검색 지역 선택에 시군구 추가. 값 형식은 3절 H3

### B2. 지역 목록 API 추가
- **제안**: `GET /api/regions` → 시도별 시군구 목록 (코드, 표시명, "○○ 전체" 포함)
- **이유**: 프론트가 시군구 목록을 하드코딩하지 않게. 행정구역이 바뀌어도(예: 통합특별시) 백엔드 데이터만 고치면 됨

### B3. 세션 관심 분야(`category`) 빼기 (§4.1 `POST /api/sessions`, `ChatSession.category`)
- **제안**: 세션 생성의 필수 `category`를 없앤다
  - 세션 제목: 서버가 **첫 질문**으로 만든다 (예: "서울 주거 지원 정책 알려줘"). 첫 질문 전에는 "새 대화"
  - 추천 정책: 그 세션 **대화에서 나온 분야** 기준. 대화 전이면 프로필 기준으로 신청 가능한 정책
- **이유**
  - 채팅 답변은 질문마다 분야를 직접 판단해서, 세션을 만들 때 고른 분야가 답변에 거의 반영되지 않는다
  - 정책 분류가 엇갈리는 경우가 있어(예: 창업자 월세 지원이 일자리 분류) 분야로 거르면 맞는 정책이 빠진다
  - "주거로 만든 채팅방에서 취업을 물어도 되나", "다른 분야는 방을 새로 만들어야 하나" 같은 혼란이 생기고, 필수 입력 단계만 늘어난다
- 차선책 (유지를 원하면): 선택 입력 + 여러 개 선택 + 답변 필터로는 쓰지 않고 추천에만 사용
- 프론트 영향: 세션 생성 화면에서 분야 선택 제거. 채팅 화면에서 정책 검색을 열 때 세션의 카테고리를 미리 고르던 동작이 없어짐 (지역만 미리 고름)

### B4. 조건 처리: 프로필로 거르고, 다르면 되묻기 (채팅 동작)
- **제안**
  - 정책은 **채팅방 프로필로만** 거른다. 채팅방 프로필은 만든 뒤 수정할 수 없다 (한 채팅방 안에서 답변 기준이 같아야 기록을 믿을 수 있음). 조건이 바뀌면 새 채팅방
  - 질문에 프로필과 다른 **지역·나이**가 있으면 정책을 찾지 않고 되묻는다 (일반 `token` 답변, 카드 없음. 백엔드 구현됨, #35)
    ```
    질문에 말씀하신 지역(인천)이 프로필 지역(서울특별시 강남구)과 달라요.
    - 프로필 기준으로 찾으려면 지역을 빼고 다시 물어봐 주세요.
    - 말씀하신 조건으로 찾으려면 프로필을 그 조건으로 정한 새 채팅방에서 물어봐 주세요.
    ```
    - 지역은 B1의 필터 범위(고른 시군구 + 시도 전체 + 전국) 밖이면 다른 지역으로 본다. 강남구 프로필에 "서초구 청년 지원"은 되묻기, "서울 청년 지원"은 검색
    - 나이도 같은 형식. 지역·나이가 둘 다 다르면 한 문구로
    - 어느 지역인지 알 수 없는 지명("판교")은 되묻지 않고 프로필 기준으로 찾은 뒤 답변에서 알린다
  - 질문의 **취업 상태·학력**이 프로필과 다르면 되묻지 않고 프로필 기준으로 찾은 뒤 답변에서 다르다고 알린다 ("대학원생도 받을 수 있어?" 같은 가정 질문이 많음)
  - "지금 신청 가능한 것만"은 질문에서 바로 반영한다
  - 이미 보여 준 정책을 가리킨 질문("두 번째 거 인천 사람도 받을 수 있어?")은 되묻지 않고 답변에서 자격을 설명한다
- **이유**: 질문에서 조건을 뽑아 거르면, 추출이 틀렸을 때 맞는 정책이 조용히 빠진다. 되묻기로 바꾸면 추출이 틀려도 안내 문구만 틀린다
- 프론트 영향: 없음 (되묻기는 일반 답변). 버튼은 3절 H4

### B5. 정책 신청 상태 `status` 필드 추가 (`PolicySummary`, 채팅 카드)
- **제안**: `status`: `OPEN`(신청 가능) / `ALWAYS_OPEN`(상시) / `UPCOMING`(신청 예정) / `CLOSED`(마감) / `UNKNOWN`(기간 정보 없음). D-day는 `OPEN`·`UPCOMING`일 때만 표시
- **이유**: 날짜만으로는 상시 모집, 기간 정보 없음, 기간이 남았는데 조기 마감된 정책(마감 코드)을 구분할 수 없다. 서버가 한국 날짜 기준으로 계산해 답변 본문과 같은 값을 준다

### B6. 정책 지역은 표시 문구로 (`PolicySummary.region`)
- **제안**: `region`(시도 코드 하나) 대신 표시 문구 `regionLabel`: "서울특별시 강남구", "경기도 5곳", "서울특별시 외 14개 시도", "전국"
- **이유**: 정책 지역이 여러 곳(2~16곳)이거나 시군구 단위인 경우가 많아 코드 하나로 표현이 안 된다

### B7. 정책 상세의 필드와 문구 (§4.3 `PolicyDetail`)
- **제안**
  - 신청 방법이 비어 있으면 "공고에 나와 있지 않음" 문구 (신청 가능한 정책의 약 55%가 비어 있음)
  - 제출 서류는 목록이 아니라 문자열 하나 (원본이 자유 문장)
  - 링크 버튼 문구는 "신청하기"가 아니라 **"관련 사이트"**처럼 중립적으로 (링크의 절반 이상이 기관 홈페이지 첫 화면)
  - 문의처로 담당 기관 필드 `organization` 추가

### B8. 채팅 카드 번호 배지와 순서
- **제안**: 채팅 카드에 번호 배지 표시 (`policies` 배열 위치 + 1)
- **이유**: 답변 본문은 정책을 "1. 2. 3."으로 소개하고, 챗봇은 "두 번째 정책 신청 방법은?"을 카드 순서로 이해한다. 카드에 번호가 없으면 사용자가 세어야 함
- 채팅 카드 순서는 질문 관련도 기준이라 검색·스크랩 정렬(§4.3)과 규칙이 다르다

### B9. SSE에서 카드(`policies`)를 답변 본문 시작 직전에 보냄 (§5.2)
- **제안**: 카드가 있는 답변은 **모두** `policies` 이벤트를 첫 `token` **바로 앞**에 보낸다. 계약상 "`done` 전"이면 허용되는 순서
  - 검색 답변: LLM이 답변 첫 줄에 고른 카드 번호를 쓰므로, 서버가 첫 줄까지 받아 카드를 정한 뒤 `policies` → 본문 `token`을 이어 보냄
  - 상세 답변·되묻기처럼 카드가 미리 정해진 경우도 **같은 시점**(본문이 시작될 때)에 보냄. 질문 종류에 따라 카드가 뜨는 시점이 달라지지 않게
  - 카드가 없는 답변(인사, 조건 되묻기 등)은 `policies`를 보내지 않음
- **이유**: 답변 생성에 10초 이상 걸리는 경우가 있어, 본문이 끝날 때까지 기다리지 않고 카드를 먼저 보여 주면 체감 대기 시간이 줄어든다. 첫 줄이 나오기까지의 시간(질문 분석, 검색, LLM 첫 출력)은 그대로라 카드가 "즉시" 뜨지는 않음
- 확인 부탁: 프론트가 `policies`를 받는 즉시 카드를 그리는지
