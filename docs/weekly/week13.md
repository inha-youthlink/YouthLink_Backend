## 3. 결정과 정할 것

**결정 (11-23): 채팅 범용 경로를 에이전트로 바꾸지 않음** (12주차 3절 "이후 검토"에서 이어짐)
- 하이브리드(라우터 + 에이전트)는 분석(LLM 1번) → 에이전트 도구 루프(2~3번) → 답변 생성(1번)이 되어, 지금 2번인 LLM 호출이 4~5번으로 늘고 추천 첫 글자가 약 5초에서 8~9초로 늦어짐
- 호출을 1번만 늘리는 "검색 계획 1회"는 분석이 이미 하위 질문마다 검색어·분야·`local_only`·신청 상태를 내는 일과 겹쳐 얻는 것이 적음
- 막혔을 때만(후보 0개 등) 에이전트를 부르는 방식도 검토함. 막다른 경우가 얼마나 자주 나오는지 모르고, 남은 기간에 채팅 흐름을 바꾸면 시연이 흔들릴 수 있어 하지 않음
- 대신 역할을 나눔: 채팅은 분명한 질문에 빠르고 확실하게(라우터형), 무엇을 물을지 모를 때의 탐색은 추천 패널(에이전트형)
- 에이전트를 채팅에 넣으려던 목적(예상 못 한 정책 질문에 대응)은 LLM 호출을 늘리지 않는 아래 세 가지로 메꿈

**예상 못 한 질문 보완 (LLM 호출 수 그대로)**

| | 막히는 곳 | 보완 | 바뀌는 곳 |
|---|---|---|---|
| ① | 정책 관련인데 기준이 애매한 질문이 `unclear`로 분류되어 고정 문구 되묻기로 끝남 (12주차 비교 "나한테 제일 이득인 정책 하나만 골라줘") | 되묻기 문구에서 대화로 좁혀 주는 정책 추천 에이전트를 안내 (11-24 바꿈, 아래) | `handlers/clarify.py` 고정 문구 |
| ② | 복합 질문(하위 질문 2개 이상)은 검색어를 이어 붙여 한 번만 검색해 한쪽 결과가 후보에서 밀려남 | 하위 질문 종류별로 처리 (추천은 따로 검색, 지목은 고정, 범위 밖·되물을 것은 안내), 카드는 묶음마다 1개 이상 | 새 복합 질문 핸들러 `handlers/composite.py`, 라우터, 생성기 |
| ③ | 공고로 판단할 수 없는 기준("덜 알려진", "혜택 큰")을 답변이 판단한 듯 말함 | 판단할 수 없는 기준은 먼저 밝히고, 근거로 말할 수 있는 것만 말하고, 좁힐 방법을 제안 | 답변 지시문 `answer_recommend_v2` |

- PR은 둘로 나눔: PR 1 = ②③ (검색·답변, 분석은 그대로), PR 2 = ① (되묻기 문구)
- 계약 형식은 바뀌지 않음. ①은 되묻기 문구만 바뀌어 계약 5.3에 동작 한 줄 보충
- ① 11-24 바꿈: 처음엔 분석 v11로 이런 질문을 추천 경로로 보내려 했음. 그런데 실제로 `unclear`로 빠지는 건 분야도 없는 질문("제일 이득인 거 하나만")이고, 분야가 있는 질문은 v10에서도 추천으로 가 ③이 처리함. 분야도 기준도 없는 질문은 질문을 주고받으며 좁히는 추천 에이전트가 맞고, 분석을 바꾸면 v10과 나란히 측정해야 해서(분석 약 420회) 되묻기 문구 안내로 바꿈. 분류는 그대로라 평가 서버 라우팅 정답과도 겹치지 않음

**정한 것 (11-24, 자세한 것은 [design.md](../design.md) 8-5)**
- ①: 되묻기 문구 안내. 에이전트 이름은 프론트 패널 버튼과 같아야 함 ("정책 추천 에이전트", 계약 0절)
- ②: 하위 질문을 두 갈래로만 나눔 (근거 모음: 검색·지목 / 답하지 않음: 범위 밖·어느 정책인지 모름·비교·카드 3자리 넘음). 후보는 하위 질문마다 단일 질문과 같은 방법으로 만든 뒤 번갈아 6자리를 채우고 질문 순서대로 놓음. 상세 + 추천은 지목 고정 + 추천 묶음. 복합 안의 비교는 대상별 카드 규칙이 겹쳐 조건이 계속 늘어 안내로 돌림
- ③: 규칙 두 줄 + 예시 한 줄 (판단할 수 없는 기준은 먼저 밝힘, 금액·기간처럼 근거에 있는 기준은 그 값으로)
- 확인용 질문 세트 31개로 전·후 나란히 (결과 문서). 최종 코드로 31개 전체를 다시 재지는 않음 (한도), 고친 부분은 해당 질문으로 확인

**회귀 평가**
- 직접 돌리지 않고 PR 뒤 평가 서버 담당에게 한 번에 요청 (평가·배포 모두 담당을 기다리는 일이라 묶음)
- 라우팅 `routing_v1` 90건: v8과 PR 뒤 `main`(v10)을 나란히. 분석 지시문이 12주차와 같고 라우팅 평가는 intent만 봐서 12주차 상태(`a28e4c1`)는 `main`과 같음. Titan 기준점이 없어서 v8도 같은 조건으로 다시 돌림. 평가 서버 쪽에 Titan 결과가 있으면 그것을 씀. 라우팅 평가는 trace의 `analysis.sub_queries[].intent`만 봄
- 답변·검색 `golden_v2` 100건: 12주차 상태와 PR 뒤 `main`을 1회씩 (채점 비용). 바뀐 곳은 단일 추천 답변 지시문(v2)과 복합 질문이라 단일 추천 문항의 답변 지표를 전·후로 비교하고, 복합 문항은 따로 표시해서 봄 (복합은 하위 질문별 검색 청크를 합쳐 기록해 청크 수가 많을 수 있음)
- 한도를 받은 뒤에 요청 (2절)
- `local_only`는 라우팅 세트에 없는 필드라 12주차 시험 세트(44개)로 확인한 것으로 갈음

**관찰에서 이어진 것**
- 현재 정책이 둘일 때 이름 없이 "신청 기간은?": (11-24 정함) 되묻기 그대로 (10주차 정답, "어느 정책을 말씀하시나요?" + 두 정책)
