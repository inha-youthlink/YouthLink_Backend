## 1. 목표

## 3. 결정과 정할 것

**결정 (11-23): 채팅 범용 경로를 에이전트로 바꾸지 않음** (12주차 3절 "이후 검토"에서 이어짐)
- 하이브리드(라우터 + 에이전트)는 분석(LLM 1번) → 에이전트 도구 루프(2~3번) → 답변 생성(1번)이 되어, 지금 2번인 LLM 호출이 4~5번으로 늘고 추천 첫 글자가 약 5초에서 8~9초로 늦어짐
- 호출을 1번만 늘리는 "검색 계획 1회"는 분석이 이미 하위 질문마다 검색어·분야·`local_only`·신청 상태를 내는 일과 겹쳐 얻는 것이 적음
- 막혔을 때만(후보 0개 등) 에이전트를 부르는 방식도 검토함. 막다른 경우가 얼마나 자주 나오는지 모르고, 남은 기간에 채팅 흐름을 바꾸면 시연이 흔들릴 수 있어 하지 않음
- 대신 역할을 나눔: 채팅은 분명한 질문에 빠르고 확실하게(라우터형), 무엇을 물을지 모를 때의 탐색은 추천 패널(에이전트형)
- 에이전트를 채팅에 넣으려던 목적(예상 못 한 정책 질문에 대응)은 LLM 호출을 늘리지 않는 아래 세 가지로 메꿈

**예상 못 한 질문 보완 (LLM 호출 수 그대로)**

| | 막히는 곳 | 보완 | 바뀌는 곳 |
|---|---|---|---|
| ① | 정책 관련인데 기준이 애매한 질문이 `unclear`로 분류되어 고정 문구 되묻기로 끝남 (12주차 비교 "나한테 제일 이득인 정책 하나만 골라줘") | 분석이 "정책 관련인데 애매함"과 "의미 불명"을 나누고, 앞의 것은 추천 경로로 | 분석 지시문 `analyze_v11`, 라우터 |
| ② | 복합 질문(하위 질문 2개 이상)은 검색어를 이어 붙여 한 번만 검색해 한쪽 결과가 후보에서 밀려남 | 하위 질문 종류별로 처리 (추천은 따로 검색, 지목은 고정, 범위 밖·되물을 것은 안내), 카드는 묶음마다 1개 이상 | 새 복합 질문 핸들러 `handlers/composite.py`, 라우터, 생성기 |
| ③ | 공고로 판단할 수 없는 기준("덜 알려진", "혜택 큰")을 답변이 판단한 듯 말함 | 판단할 수 없는 기준은 먼저 밝히고, 근거로 말할 수 있는 것만 말하고, 좁힐 방법을 제안 | 답변 지시문 `answer_recommend_v2` |

- PR은 둘로 나눔: PR 1 = ②③ (검색·답변, 분석은 그대로), PR 2 = ① (분석 지시문이 바뀌어 따로 측정)
- 계약 형식은 바뀌지 않음. ①로 동작이 바뀌면(애매한 질문에 되묻기 대신 추천) 계약 보충

**정할 것 (PR 구상 때)**
- ①: 분석 출력에 표시를 더할지, intent 정의만 바꿀지. 평가 서버 라우팅 정답(`routing_v1`의 `expected_intent`)과 어긋나지 않는지. 12주차처럼 개발 세트 + 시험 세트 44개로 v10과 나란히
- ②: 하위 질문마다 후보 몇 개씩 가져올지, 합치는 순서(번갈아 vs 점수), 의도가 섞인 복합 질문(상세 + 추천)은 어떻게 할지
- ③: 일반 규칙만 둘지, 예시도 넣을지
- 확인용 질문 세트: 주관적 기준 3개(12주차 비교), 복합 질문, 애매한 정책 질문, 일반 추천 몇 개. 바꾸기 전·후 나란히 (12주차 `run_chat_vs_agent.py`의 채팅 쪽)

**회귀 평가**
- 직접 돌리지 않고 PR 뒤 평가 서버 담당에게 한 번에 요청 (평가·배포 모두 담당을 기다리는 일이라 묶음)
- 라우팅 `routing_v1` 90건: v8, 12주차 상태(`a28e4c1`, v10), PR 뒤 `main`(v11)을 나란히. Titan 기준점이 없어서 v8도 같은 조건으로 다시 돌림. 평가 서버 쪽에 Titan 결과가 있으면 그것을 씀. 라우팅 평가는 trace의 `analysis.sub_queries[].intent`만 봄
- 답변·검색 `golden_v2` 100건: 12주차 상태와 PR 뒤 `main`을 1회씩 (채점 비용)
- `local_only`는 라우팅 세트에 없는 필드라 12주차 시험 세트(44개)로 확인한 것으로 갈음

**관찰에서 이어진 것**
- 현재 정책이 둘일 때 이름 없이 "신청 기간은?": 되묻기(10주차 정답)와 둘 다 답하기 중 어느 쪽을 정답으로 둘지

## 4. 작업 순서 (11-23 바꿈)

| 순서 | 작업 | 최소 완료 기준 |
|---|---|---|
| 1 | PR 1: 복합 질문 핸들러 + 추천 답변 규칙 (②③) | 확인용 질문 세트로 전·후 나란히, 테스트 통과 |
| 2 | PR 2: 분석 v11 (①) | 개발 세트·시험 세트 44개로 v10과 나란히, 떨어진 유형이 없거나 원인 확인 |
| 3 | 팀원 전달 | 평가 요청(3절), 배포 요청(022 먼저 → 서버), 프론트 mock 걷기(에이전트 API 실제 연결, 질문 없는 턴에도 직접 입력, v1.4 보충), ETL 지역 데이터 확인 거리 (광양시 정책 4개가 전국 지역 코드, 경기 프로필에 충청북도 취업박람회 등). 프론트·평가 서버·인프라가 한 사람이라 묶어서 전달 |
| 4 | 평가 확인 → 배포 | 라우팅에서 떨어진 유형이 없거나, 있으면 틀린 샘플로 원인 확인. 떨어지면 그 PR의 지시문만 되돌리거나 12주차 상태(`a28e4c1`)로 배포. 운영 DB에 022 먼저 → 서버 배포 → 운영에서 채팅·추천 에이전트·PDF·스크랩 한 바퀴 |

- 순서를 바꾼 이유: 배포·평가는 평가 서버·인프라 담당을 기다리는 일이라, 보완 PR을 먼저 끝내고 평가·배포를 한 번에 요청함
- PR은 12주차처럼 로컬 확인 뒤 머지함. 배포할 커밋은 평가 뒤 정함
- 되돌리기: 분석은 `analyzer.py`의 `PROMPT_NAME`, 답변은 `generator.py`의 `KIND_PROMPTS` 한 줄. 시연은 12주차 상태로도 가능
- PR은 main에서 새 브랜치
