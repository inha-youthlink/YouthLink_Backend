# 7주차 작업 계획 (2026-10-13 ~ 10-18)

> 목표: **저장된 대화로 후속 질문에 답하는 챗봇**
> 설계 기준 문서: [design.md](../design.md)

---

## 1. 목표

6주차에 대화를 저장하는 흐름을 만들었지만, 파이프라인은 아직 질문 하나만 보고 답한다. 7주차에는 저장된 대화와 상태를 파이프라인에 넘기고, 질문을 분석해 후속 질문("두 번째 거", "그 정책 서류는?")에 답한다.
함께 질문 유형별 처리(핸들러)와 신청 상태 기준의 정렬·필터링을 시작한다.

| 주차 | 작업 |
|---|---|
| 7주차 | 질문 분석(상태 신호 포함), 현재 정책 상태, 핸들러 확장(유형별 답변 명세 먼저), 신청 상태 우선순위, 1차 필터링 (`design.md` 16절) |
| 8주차 | 자격 확인·비교 핸들러, 관련성 판정, 실제 데이터로 RAG 평가 (11절) |

**성과 기준**: 6주차 채팅 저장 확인에서 틀린 질문이 풀리는지 ([week06.md](week06.md) 11절)
- "서울 주거 지원 정책 알려줘" → "두 번째 정책 신청 방법은?"에 직전 답변의 두 번째 정책(청년 이사비 지원)으로 답한다
- 카드 순서와 본문 순서가 같다

## 2. 범위

| 하는 것 | 하지 않는 것 |
|---|---|
| 실제 데이터로 로컬 DB 구성, 신청 상태 질문 세트 (6주차 이월) | 자격 확인·비교 핸들러 (8주차) |
| 질문 분석, 파이프라인 입력에 대화·상태 추가 | 복합 질문의 여러 하위 질문 실행·결합 (8주차, 비교와 함께) |
| 현재 정책 목록 갱신 | 관련성 판정 (8주차) |
| 핸들러: 범위 밖, 정책 상세 (+ 정책 목록) | 지역 필터링 (8주차, 자격 확인과 판정 로직 공유) |
| 신청 상태 우선순위 v1, 카드·본문 순서 일치 | 스트리밍 (Spring 연동 전 결정) |
| 1차 필터링 (첫 조건은 신청 상태) | Advanced RAG 기법 (12~13주차) |
| (시간이 되면) 지역 표시: 프로필 지역 이름, 근거의 `[대상 지역]` | |

**전제**
- `pipeline/`은 DB에 쓰지 않는다. 현재 정책 목록 갱신도 파이프라인은 결과만 돌려주고 저장은 `services/`가 한다
- `PipelineInput`/`PipelineOutput`에는 기본값 있는 선택 필드만 추가한다. 한번 넣으면 바꿀 수 없으므로 형태를 정한 뒤 추가한다
- 핸들러 추가 원칙 (`design.md` 9절): 기본 경로(`default_rag` + 질문 분석)로 시작하고, 실패 사례를 보고 필요한 곳만 분리한다

## 3. 작업 순서

작업마다 PR을 나눈다. 중간에 멈춰도 각 단계가 동작하는 상태로 남도록 최소 완료 기준을 둔다.

| 순서 | 작업 | 최소 완료 기준 | 시간이 되면 |
|---|---|---|---|
| 1 | 질문 분석 + 대화 입력 | intent, 질문 재작성, 정책 지목. `PipelineInput`에 대화·상태 추가 | 상태 신호 추출 |
| 2 | 현재 정책 상태 | 설정·교체·초기화 규칙, `chat_current_policy` 갱신 | 여러 개일 때 후속 질문 처리 |
| 3 | 핸들러 확장 | 답변 명세(정책 상세) → 범위 밖 → 정책 상세 (`policy_ids`) | 정책 목록 (SQL 조회) |
| 4 | 실제 데이터 DB 구성 (이월) | VWorld 키 발급, ETL 절차로 DB 구성 + 008 적용 | 지역 표시 (7절) |
| 5 | 신청 상태 우선순위 v1 | 질문 세트(이월), 상태 순서 규칙, 카드·본문 순서 일치 (C 방식, 6절) | 기간이 두 개인 정책 판정 |
| 6 | 1차 필터링 | 신청 상태로 `policy_ids` 제한 | 단계적 완화 |

- 1~3번은 가짜 데이터로 진행한다
- 5~6번은 실제 데이터의 상태 분포로 규칙을 정해야 하므로 4번 이후에 한다
- 1번이 가장 중요하다 (`design.md` 8절 "가장 중요한 단계"). 1~2번까지가 이번 주 핵심이다

## 4. 질문 분석

질문 하나에 LLM 호출이 하나 늘어난다 (분석 1회 + 답변 1회). LLM은 분석 결과만 출력하고, 핸들러 선택은 코드가 한다 (`design.md` 8절).

### 입력
| 정보 | 출처 | 비고 |
|---|---|---|
| 질문 | 요청 | |
| 최근 대화 | `chat_message` 최근 3턴 (결정 1) | 긴 답변 자르기 기준은 이번에 정함 |
| 직전에 보여준 정책 | `message_policy_ref`, `display_order` 순 | "1. 청년 월세 지원"처럼 번호 + 이름 |
| 현재 정책 목록 | `chat_current_policy` | |
| 프로필 | `chat_profile` | 지금처럼 답변 생성에도 사용 |

### 출력 (초안, 이번에 확정)
- 처음부터 **하위 질문 목록** 형태 (`design.md` 8-5). 단일 의도는 길이 1
- 하위 질문마다: intent, 재작성된 질문, 대상 정책 번호, 상태 신호("지금 신청 가능한 것만", "마감된 것도")
- 전체: 화제 전환 여부
- 7주차 실행 범위: 하위 질문 1개만 정상 경로, 2개 이상은 `default_rag`

### 검증 (`design.md` 8-3)
- 후보(보여준 정책, 현재 정책)에 없는 정책 번호 → 버리고 되묻기
- 애매한 분류 → `default_rag`
- 스키마 오류 → 재시도 또는 기본값

### 정할 것
- 출력 스키마 필드와 intent 범주 (`schemas/analysis.py`)
- `PipelineInput` 추가 필드 형태 (6주차 결정 3에서 미룬 것): 보여준 정책을 번호만 넘길지 이름까지 넘길지, 대화를 질문·답변 쌍으로 넘길지, 긴 답변 자르기
- 분석용 모델 (출력이 짧아 빠른 모델 검토)
- 프롬프트 `analyze_v1`과 few-shot 예시
- 분석 결과를 답변 `metadata`에 저장하는 키 (6주차 결정 5)

## 5. 현재 정책 상태

| 상황 | 처리 |
|---|---|
| 설정 | 정책 하나를 지목하거나 자세히 다룬 경우 |
| 교체 | 다른 정책을 명확히 지목 |
| 초기화 | 화제 전환 |
| 여러 정책 | 비교·복합 질문이면 목록으로 저장 (6주차 결정 7) |

- 파이프라인은 갱신된 현재 정책 목록을 `PipelineOutput`의 선택 필드로 돌려주고, `chat_service`가 `save_turn`과 같은 트랜잭션에 저장한다
- 정할 것: 현재 정책이 여러 개일 때 이름 없는 후속 질문을 전부 답할지 되물을지, 최대 개수 (`design.md` 8-4)
- `save_turn`이 바뀌므로 저장소 테스트에 현재 정책 교체 테스트를 추가한다

## 6. 핸들러 확장과 답변 형식

### 순서
1. **답변 명세 먼저** (`design.md` 12-1): 정책 상세부터. `docs/answer_spec.md`
2. 범위 밖: 검색 없이 고정 문구
3. 정책 상세: 대상 정책이 있으면 `policy_ids`로 그 정책의 청크 안에서만 검색
4. (시간이 되면) 정책 목록: SQL 조회
- 핸들러는 **근거만 반환**하고 답변 생성은 마지막에 한 번 (`design.md` 9절). 나중에 복합 질문·비교를 붙이기 위함

### 근거 구성: 청크로 찾고, 정책 원본으로 답한다 (`design.md` 10-5)
ETL 청크가 정책당 최대 4개(요약·자격·지원·신청)로 바뀌어, 검색된 청크만 근거로 쓰면 필요한 섹션이 빠질 수 있다 (예: 소득 질문에 `SUMMARY`만 검색됨).
- 청크는 어떤 정책을 찾을지에만 쓰고, LLM에 넘기는 근거는 `policy` 원본 필드로 구성한다
- 6주차에 발견한 근거 중복(`APPLICATION` 청크와 `[신청 방법]`·`[제출 서류]`)도 함께 정리된다
- 원본 전체는 길어 응답이 느려질 수 있으므로 핸들러마다 근거 범위를 정한다: 정책 상세(정책 1개)는 전체, 정책 목록(여러 개)은 카드 정보 + 요약 (답변 명세와 함께)
- 근거 구성을 바꾸면 debug의 `contexts`도 바뀐다. 평가 서버 결과를 비교할 때 `prompt_version`과 함께 기록한다

### 답변 형식: 카드는 목록, 본문은 설명 (C 방식, 7주차 결정)
| | 역할 | 내용 |
|---|---|---|
| 정책 카드 (`policies`) | **목록의 기준** | 최소 정보: 번호, 정책 이름, 신청 상태, 마감일, 신청 링크 |
| 답변 본문 | 설명 | 카드와 **같은 번호·순서**로, 프로필 기준 설명 |

- 카드의 순서와 개수는 **코드가 정한다** (신청 상태 우선순위, 상위 N개). LLM은 주어진 번호 순서대로 모두 소개한다
- 이유
  - "두 번째 거"의 기준이 하나가 된다 (코드 순서 = 카드 번호 = `display_order` = 본문 번호)
  - 카드와 본문 순서가 어긋나지 않는다 (6주차 관찰)
  - 카드가 답변 생성 전에 정해져 나중에 스트리밍을 붙이면 카드를 먼저 보낼 수 있다
- 카드에서 정책을 빼는 판단(관련 없음)도 답변 생성 전에 코드가 한다. LLM이 소개한 정책으로 카드를 정하는 방식은 쓰지 않는다
- 바뀌는 것
  - 묶인 정책 전체가 아니라 상위 N개만 카드·근거로 사용
  - `generate_v1`의 "마감 정책은 뒤에", "최대 5개" 규칙을 코드 정렬·개수 제한으로 옮기고, 프롬프트에는 "번호 순서대로 모두 소개"를 둔다
  - `PolicyItem`에 신청 상태 선택 필드 추가 검토

## 7. 신청 상태 우선순위와 1차 필터링

실제 데이터의 상태 분포가 필요해 4번(DB 구성) 이후에 한다.

**신청 상태 우선순위 v1** (`design.md` 10-4 "정할 것" 확정)
- 질문 세트 초안 (6주차 이월): 신청 가능 정책이 있는 경우, 마감 정책만 있는 경우, 마감 정책을 지목한 경우, 마감 포함을 요청한 경우
- 상태 순서, 질문 유형별 적용(목록은 적용, 상세는 적용 안 함), 마감 정책을 보여줄 조건
- 질문 분석의 상태 신호로 적용 여부를 바꾼다
- (시간이 되면) 기간이 두 개인 정책 판정: `policy_application_period`(ETL 006)를 읽어 판정

**1차 필터링** (`design.md` 10-2)
- 첫 조건은 신청 상태. 결과를 `policy_ids`로 검색에 넘긴다
- 질문 유형별 적용: 목록은 적용, 지목한 정책 상세는 적용 안 함
- 지역 조건은 8주차에 추가한다 (자격 확인 핸들러와 판정 로직 공유)

**지역 표시** (시간이 되면, [week06.md](week06.md) 4절)
- ETL #3이 닫혀(007: 인천 보정, `v_policy_region_scope`·`v_policy_sido_scope`) 6주차에 미룬 조건이 충족됐다
- 프로필 지역 코드를 이름으로 표시하고, 근거에 정책의 `[대상 지역]`("전국", "서울특별시 전체" 등)을 넣는다
- 범위 판정은 ETL View를 그대로 쓴다. RAG가 따로 계산하지 않아 백엔드와 판정이 같아진다
- 지역 테이블이 있는 DB가 필요해 4번 이후에 한다
- 참고: ETL 새 청크의 `ELIGIBILITY`에 지역 이름이 들어가 검색에는 이미 어느 정도 반영된다

## 9. 확인 환경

- 1~3번은 5주차 가짜 데이터(`youthlink_chat`)로 개발하고, 4번 이후 실제 데이터로 다시 확인한다
- 6주차 관찰 질문을 확인 질문으로 쓴다: "서울 주거 지원 정책 알려줘" → "두 번째 정책 신청 방법은?" → "소득 기준은?"
- 저장소 테스트(`uv run pytest`)는 계속 통과해야 한다. `save_turn` 등 저장소를 바꾸면 테스트를 함께 추가한다
- 질문 분석 추가로 응답 시간이 늘어난다. 답변 `metadata.latency_ms`로 분석 구간 시간을 확인한다
