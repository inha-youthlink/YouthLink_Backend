# 10주차 작업 계획 (2026-11-03 ~ 11-08)

> 목표: **중간시연(11주차) 준비. 프론트가 계약 하나만 보고 붙을 수 있게 하고, 발표 피드백에 맞춰 질문 분기(비교·복합 질문)를 늘림**
> 설계 기준 문서: [design.md](../design.md), 공개 API 계약: [api-contract.md](../api-contract.md) v1.0. 이 문서에는 10주차의 결정과 근거, 작업 순서를 남긴다

---

## 1. 목표

9주차에 공개 API를 가이드 PDF만 빼고 모두 구현했다 ([week09.md](week09.md) 7절). 10주차에는 프론트에 넘길 계약을 하나로 정리하고, 발표 피드백(2절)에 맞춰 라우팅 설명과 답변 규칙을 다듬고, 핸들러를 늘린다(비교 → 복합 질문). 새 임베딩 기준으로 평가 점수와 라우팅 정확도를 잰다.

**일정**
- 중간시연: 11주차 (질문 이해 + 기본 분기 + 근거 기반 답변)
- 끝내지 못한 항목은 11주차로 넘긴다

## 2. 상황 (11-05)

| 대상 | 상황 |
|---|---|
| 발표 피드백 | "핸들러를 결정하는 건 코드인데, 챗봇의 많은 변수를 감당할 수 있는가?" → 발표에서 "경로는 규칙 코드가 정한다"를 강조해 자연어를 규칙으로 처리하는 구조로 들렸고, 테스트 수치가 없어 근거를 보여 주지 못함 |
| 프론트 | 계약 회신 없음. 코드는 아직 v0.3 형식 (타입, 카드 검사, mock) |
| 인프라 | 서버 아직 안 뜸. 운영 DB는 실수로 다시 임베딩한 Titan DB여야 함 ([deploy.md](../deploy.md)) |
| 평가 서버 | 채점·데이터셋 생성의 임베딩이 이진(0/1)으로 오는지 확인 필요 (9주차 임베딩 이진 문제와 같은 원인일 수 있음) |
| ETL | 운영 DB 청크 재임베딩(`--force`) 필요 |

- 프론트·평가 서버·인프라는 한 사람이 맡고 있어, 전달 사항은 묶어서 보낸다

**지금 라우팅 (코드 기준)**: 경로는 사실상 질문 분석(LLM)이 고른 의도로 정해진다. 라우터(`pipeline/router.py`)는 의도를 핸들러에 대응시키고, 코드가 직접 판단하는 것은 질문의 지역·나이가 프로필과 다를 때 되묻는 것 하나다. 즉 **LLM 의도 분류 기반 라우팅 + 규칙 기반 안전장치**이고, 규칙 기반 라우팅이 아니다.

## 3. 결정

**공개 API 계약**
| 결정 | 내용 | 이유 |
|---|---|---|
| 계약 v1.0 | `api-contract.md` 하나로 정리 (프론트 초안 v0.3 없이 읽힘). 맨 앞에 "프론트가 바꿀 것" 체크리스트. 구현 현황 문서 `front-sync.md`는 합치고 지움 | 잠정본은 "여기 없는 건 v0.3 그대로"라 두 문서를 함께 읽어야 했고, 구현 현황 문서와 내용이 겹쳤음 |
| 카드 개수와 번호 | 채팅 카드 최대 10개. 번호는 답변마다 1부터 ("더 알려줘"로 이어 받은 정책도 새 카드만, 본문도 1부터) | 번호로 묻는 질문("두 번째 거")은 직전 답변 카드 기준이라 지금 동작과 같음. 카드에 번호 필드를 넣으면 프론트 타입이 바뀌고 "두 번째"가 어느 번호인지 헷갈림 |
| 답변 마크다운 범위 | CommonMark만 (표 없음). 정책 비교도 항목별 목록 | 프론트는 `react-markdown`만 쓰고 표 확장(`remark-gfm`)이 없음. 채팅 말풍선이 좁아 모바일에서 표가 읽기 어려움 |
| 가이드 PDF 형식 | v0.3 형식 그대로 확정 (동기, `201 {policyId, pdfUrl, expiresAt}`, 만료 10분 이하). 넣을 항목·저장 위치는 구현 때 | 프론트 mock이 이미 이 형식. 나중에 형식을 정하면 프론트를 다시 고쳐야 함 |
| 뼈대 삭제 시점 | 배포 경로에서 뼈대(긴 스트림)와 실제 RAG를 모두 확인한 뒤 삭제. 남겨 두지 않음 | 켜져 있는 동안 `/chat`이 실제 답변을 하지 않아, 운영에서 켜진 채 남으면 시연이 깨짐. 다시 필요하면 git 기록에서 되살림 |
| 과도기 호환 삭제 시점 | 프론트가 v1.0 반영을 알려 주면 지움 (날짜로 정하지 않음) | 프론트 일정이 정해지지 않았음. 먼저 지우면 실연동이 깨짐 |

**라우팅과 답변 규칙 (발표 피드백)**
| 결정 | 내용 | 이유 |
|---|---|---|
| 설명 방식 | "LLM은 해석, 경로 선택은 코드" → **"LLM이 의도를 분류해 경로를 정하고, 코드는 안전 규칙만 적용"**. `design.md` 0절·8절도 같은 표현으로 | 실제 코드와 맞는 설명. 의도 오분류는 구조로 막을 수 없어 라우팅 평가(혼동 행렬)로 측정하고 고친다는 답으로 이어짐 |
| 범위는 정책 질문 | 정책과 관련 없는 일반 질문은 받지 않음 (일반 지식 유형·핸들러를 두지 않음). 범위 밖 질문 비율을 잰 뒤 많으면 다시 검토 | 일반 용어와 정책 이름이 겹침("청년도약계좌가 뭐야?"). 정책 질문을 일반 지식 경로로 잘못 보내면 근거 없는 정책 정보가 나감. 일반 지식이 필요한 순간은 대부분 정책을 보던 중에 생김 (아래 용어 설명으로 해결) |
| 용어 설명은 상세 답변에서만 | `answer_detail_v2`를 새로 만들어 사용자가 용어 뜻을 직접 물었고 그 용어가 공고(근거)에 나올 때만 일반 지식으로 한두 문장 설명. 공고에 없는 용어는 같은 분야라도 설명하지 않음 (관련 여부는 공고를 보는 상세 답변이 판단, 분석은 공고를 보지 않음). 수치와 정책의 자격·금액·기간·신청 방법은 여전히 근거에서만. 추천·짧은 답변·되묻기에는 적용 안 함. 용어 질문이 상세에 닿도록 질문 분석을 `analyze_v7`로(정책 맥락이 있으면 상세, 없으면 범위 밖, 정책 이름은 정책 질문), 짧은 답변은 `answer_short_v2`로(용어 뜻도 설명하지 않고 정책과 함께 물어 달라고 안내) | 공통 규칙("근거에 없는 내용은 일반 지식으로 채우지 않음") 때문에 정책을 보다가 "중위소득이 뭐야?"를 물으면 "공고에 명시되어 있지 않다"고 답함 |
| 되묻기와 범위 밖 구분 | 지금대로. 모호함(`unclear`)은 되묻기, 뜻은 분명하지만 범위 밖(`out_of_scope`)은 짧은 답변으로 안내 | 범위 밖 질문은 다시 물어도 결과가 같음 |
| 복합 질문을 이번 주에 | 9주차의 "복합 질문은 뒤로"([week09.md](week09.md) 3절)를 바꿈. 하위 질문마다 근거를 모아(검색은 병렬) 합치고 답변 생성은 한 번 | 사용자는 실제로 한 번에 여러 개를 물음. 지금은 원래 질문 하나로 검색해 한쪽 주제가 빠지거나 섞임. 첫 글자는 지금(목록 약 8초)보다 2~4초, 전체는 30~60% 길어질 것으로 추정하지만, 두 번 나눠 묻는 것(첫 글자 8초 × 2)보다 짧음 |
| `analyze_v7` 적용 기준 | 분석만 v6/v7 비교(기존 유형 19개 × 2회, 용어·경계 12개 × 3회)와 답변까지 확인으로 넣음. 평가 세트 확인은 평가 기준점을 다시 잴 때 v7 상태로 함께 | 평가는 비용이 커 자주 못 돌림. v7은 분석 결과만 바꾸므로 기존 질문의 분석이 같으면 뒤 단계도 같음. Titan 기준 v6 점수는 원래 없어 비교 기준을 잃지 않음. 되돌리기는 `PROMPT_NAME` 한 줄. **되돌리는 조건**: 평가 기준점에서 용어가 아닌 질문의 라우팅 정확도가 v6보다 떨어지면 `analyze_v7`만 v6로 되돌림 (`answer_detail_v2`·`answer_short_v2`는 유지, 짧은 답변 v2는 그 자체로 일반 지식 답변을 줄이는 변경) |
| 핸들러 순서 | 용어 설명 → 비교(지목 없음) → 복합 질문 → 개수 지정(시간이 되면) | 피드백과 직접 이어지는 것부터. 지목한 정책 비교는 이미 상세 답변이 처리하므로 새로 할 것은 지목 없는 비교("월세 지원이랑 전세 지원 중 뭐가 나아?"). 개수 지정은 계약에 형식(카드 최대 10개)만 정해 둠 |

**하지 않기로 한 것**
| 안 | 이유 |
|---|---|
| 판단이 안 서는 질문에 검색 없이 답하는 LLM 핸들러 | 무엇인지 모르는 질문에 근거 없이 답하면 근거 기반 답변의 예외 통로가 됨 |
| 일반 지식 유형 추가 | 정책 이름과 일반 용어의 경계를 LLM이 판단할 수 없음 |
| 검색 유사도·정책명 매칭으로 경로 전환 | 정책 문서 대부분에 일반 용어가 있어 유사도가 늘 높게 나옴. 이름 매칭은 줄임말을 놓침 |
| 정책 모드 / 일반 모드 토글 | 경계 판단이 사용자에게 넘어갈 뿐이고 서비스 정체성이 흐려짐 |
| 프롬프트 A/B 테스트 | 이번 주 범위 밖 |

## 4. 작업 순서

| 순서 | 작업 | 최소 완료 기준 |
|---|---|---|
| 1 | 계약 v1.0 (문서) | 3절 계약 결정 반영, `front-sync.md` 합침 |
| 2 | 설명 방식 (문서) | `design.md` 0절·8절을 "LLM 의도 분류 + 안전 규칙"으로. 발표 흐름도도 같은 표현 (강조를 질문 분석으로, 조건 정리와 라우터는 "안전 규칙(코드)"으로 합침) |
| 3 | 용어 설명 | `answer_detail_v2`, `KIND_PROMPTS` 변경 (v1은 그대로). 용어 질문 5~10개를 직접 확인, 특히 "2026년 중위소득이 얼마야?"처럼 수치를 묻는 질문에서 금액을 지어내지 않음 |
| 4 | 비교 (지목 없음) | 비교 대상마다 근거를 모아 항목별 목록으로 비교. 지목한 비교는 지금처럼 상세 답변 |
| 5 | 복합 질문 | 하위 질문마다 근거(검색은 병렬) → 합쳐서 생성 1회. 구상 때 정할 것: 하위 질문 상한, 카드 배분, 하위 질문의 조건이 프로필과 다를 때, 섞인 의도(인사·범위 밖·모호함), trace 형식 ([design.md](../design.md) 8-5) |
| 6 | 개수 지정 (시간이 되면) | "5개 알려줘", "더 알려줘". 상한 10개, 개수가 없으면 지금처럼 |
| 7 | 평가 | 새 임베딩 기준점 + 재정렬 감점·가산점 조정. 라우팅 정확도와 혼동 행렬(routing_v1), 되묻기·범위 밖·분석 실패 비율. 평가 서버 임베딩 확인 뒤. 용어 설명의 검색 경로(지목 없이 상세로 가는 용어 질문, 예: 목록 뒤 "중위소득이 뭐야?")도 여기서 확인: routing 세트에 용어 질문 몇 개를 넣고, 공고에 없는 용어를 설명하지 않는지 봄. 공고 안의 이름형 용어("진안행복상품권카드가 뭐야?")가 정책 이름으로 분류돼 검색으로 가는 경우도 함께 |
| 선택 | 범위 밖 안내 문구 | "청년 정책과 관련해 궁금한 용어는 정책과 함께 물어봐 주세요" 같은 예시 |
| 수시 | 서버 배포 따라가기 | 서버가 뜨면 배포 경로 SSE를 뼈대 → 실제 RAG 순서로 확인 (계약 6.3), 서버 주소를 계약 6.1에. 둘 다 통과하면 뼈대 삭제 |

- 4·5는 "대상(하위 질문)마다 근거를 모아 합치기"를 함께 쓸 가능성이 큼. 비교 구상 때 복합 질문에서 다시 쓸 수 있는 모양인지 함께 본다
- 3~6은 분석·답변이 바뀌므로 평가 세트로 점수가 떨어지지 않는지 함께 확인한다. 예전 기준점(개발 24/25, 시험 8/10)은 OpenAI 임베딩 기준이라 7번 결과로 다시 비교한다
- 계약 영향 없음: 용어 설명·범위 밖 문구는 답변 내용만 바뀌고, 비교·복합 질문 답변도 계약 5.3(카드 최대 10개, 답변마다 1부터, 표 없음) 안에 들어감
- 다음 발표에서 보여 줄 수치: 라우팅 정확도와 혼동 행렬, 되묻기·범위 밖·분석 실패 비율
