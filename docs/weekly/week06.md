# 6주차 작업 계획 (2026-10-06 ~ 10-11)

> 목표: **대화 기록을 저장하는 챗봇 기반 마련**
> 설계 기준 문서: [design.md](../design.md)

---

## 1. 목표

5주차의 Naive RAG는 질문 하나에 답하고 끝난다. 6주차에는 채팅방 단위로 대화를 저장해, 후속 질문에 대응할 기반을 만든다.
함께 RAG 평가 서버 연동(debug 모드)과 데이터 분석에서 나온 문제(지역 코드, 마감 코드)를 정리한다.

| 주차 | 작업 |
|---|---|
| 6주차 | debug 모드, 지역 코드 분석, 마감 코드 수정, ERD 변경, 채팅 저장 계층 |
| 7주차 | 질문 분석, 신청 상태 우선순위, 1차 필터링, 핸들러 확장, 현재 정책 상태 (11절) |

질문 분석은 채팅 저장 다음에 한다. 질문 재작성과 정책 지목은 대화 기록이 있어야 의미가 있고, 분석 입력을 처음부터 "질문 + 최근 대화 + 보여준 정책"으로 설계하기 위해서다.

## 2. 범위

| 하는 것 | 하지 않는 것 |
|---|---|
| debug 모드 (평가 서버 연동) | 지역 코드 반영 구현: ETL 보정 이후 (4절) |
| 지역 코드 데이터 분석, ETL 전달 | 질문 분석, 핸들러 확장 (7주차) |
| 마감 코드 판정 수정 | 신청 상태 우선순위, 1차 필터링 (7주차) |
| ERD 변경, 채팅 저장 계층 | Advanced RAG 기법: 효과를 확인하려면 실제 데이터와 평가 서버가 필요 (12~13주차) |

**전제**
- 실제 정책 청크는 아직 없다. ETL 청킹이 끝나기 전에는 5주차 가짜 데이터로 확인한다
- `pipeline/`은 DB에 쓰지 않는다. 채팅 저장은 `services/`가 맡는다

## 3. 작업 순서

작업마다 PR을 나눈다. 중간에 멈춰도 각 단계가 동작하는 상태로 남도록 최소 완료 기준을 둔다.

| 순서 | 작업 | 최소 완료 기준 | 시간이 되면 |
|---|---|---|---|
| 1 | debug 모드 | 평가 서버 요청 항목 반영 | |
| 2 | 지역 코드 분석 | ETL 이슈 등록 | |
| 3 | 마감 코드 수정 | 판정과 표시 수정 | |
| 4 | ERD 변경 | ETL 이슈·PR 제출 | 머지 |
| 5 | 채팅 저장 계층 | 채팅방 생성, 질문 전송·저장, 기록 조회 | 채팅방 목록, 현재 정책 상태 갱신 |

- 4번 PR이 머지되기 전에도 로컬 DB에 마이그레이션을 먼저 적용해 5번을 개발한다
- 3번과 함께 7주차 신청 상태 우선순위를 위한 준비(확인용 질문 세트 초안, 마감 정책 가짜 데이터)를 한다 (5절)

## 4. 지역 코드

ETL이 VWorld 기반 지역 테이블을 추가해, RAG 답변에 지역 정보를 반영한다. 이번 주는 데이터 분석과 ETL 전달까지 하고, 구현은 ETL 보정 이후에 한다.

### ETL 지역 테이블 (`db/migrations/001~003`)
| 객체 | 내용 |
|---|---|
| `policy_region` | 온통청년 `zipCd` 원본 그대로 저장 |
| `region` | VWorld 현재 시군구(5자리)만 있음. 시도 행 없음 |
| `region_code_mapping` | 옛 코드 → 현재 코드 (1:N). 화성 `41590`, 천안 `44130`, 옛 인천 코드 3개 |
| `v_policy_region_resolved` | 정책별 지역을 `DIRECT`/`MAPPED`/`UNRESOLVED`로 해석. RAG는 이 View를 사용 |

### 반영 범위
- 프로필 지역을 이름으로 표시하고, 근거에 정책의 `[대상 지역]`을 추가한다
- 검색은 지금처럼 질문만 사용한다. 질문 속 지역명 추출은 질문 분석에서, 검색 제한은 1차 필터링에서 다룬다

### 온통청년 API 전체 `zipCd` 분석 (3,238건, 10-09 기준)
| 항목 | 결과 |
|---|---|
| 빈 `zipCd` | 0건. 전국 정책은 전국 시군구 코드를 모두 나열 |
| 화성·천안·옛 인천 코드 | ETL 매핑으로 해결 |
| 인천 영종구·서해구 누락 | 522건 (전국 383 + 인천 전체 139). 개편 때 1:1 변환으로 분할된 쪽이 빠진 것으로 추정. 이미 신규 코드라 매핑으로 해결되지 않음 |
| 등록 기관과 지역 불일치 | 지자체 등록인데 전국 코드 143건 등. 답변 단계에서 처리 (이후) |

### 결정
| 주제 | 결정 | 이유 |
|---|---|---|
| 역할 분담 | 코드 보정과 전국 판정은 ETL, 표시 방식은 RAG | RAG와 백엔드가 같은 판정을 써야 함. View의 목적(변경 이력을 RAG·백엔드가 직접 처리하지 않도록)과 맞음 |
| 구현 시점 | ETL 보정 이후 | RAG가 View를 조회하므로 dev DB에 마이그레이션이 적용되기 전에는 머지할 수 없음. ETL의 제공 방식에 따라 전국 판정 설계가 달라짐. 실제 정책 청크가 없어 지금은 효과가 없음 |

ETL 전달: [ETL #3](https://github.com/inha-youthlink/youthlink-data-pipeline/issues/3) (인천 코드 보정, 전국 판정 제공, dev DB 적용 여부, VWorld와 API 코드 일치 확인)

## 5. 신청 상태 판정 (마감 코드)

### 문제
5주차에는 "API의 마감 코드는 갱신을 신뢰하기 어렵다"고 보고 상시 코드만 코드로, 나머지는 신청 날짜로 판정했다. API 전체를 분석해 보니 다음과 같다.

| 신청 코드 | 건수 | 신청 날짜 | 현재 판정 |
|---|---|---|---|
| 상시 `0057002` | 754 | 전부 비어 있음 | 상시 모집 (맞음) |
| 마감 `0057003` | 931 | **전부 비어 있음** | **정보 없음 (틀림)** |
| 특정기간 `0057001` | 1,553 | 있음 | 날짜로 판정 (맞음) |

- 마감 정책이 "정보 없음"으로 판정되어, 이미 끝난 정책을 신청할 수 있을지도 모르는 정책처럼 안내한다
- 갱신되지 않는 건 마감 코드가 아니라 특정기간 코드다 (1,553건 중 1,261건이 기간이 끝났는데 특정기간으로 남음)
- 5주차 가짜 데이터에는 마감 코드 정책이 없어 발견하지 못했다

### 결정
- 상시·마감은 코드로, 특정기간은 날짜로 판정한다
- 마감 코드이고 날짜가 없으면 기간 없이 "마감"만 표시한다

### 다음 단계: 신청 상태 우선순위 (7주차)
판정이 맞아야 우선순위도 맞으므로 이번 주는 판정 수정까지 하고, 우선순위 규칙은 7주차에 정한다 ([design.md](../design.md) 10-4).
- 7주차로 두는 이유: 우선순위는 질문 유형에 따라 다르게 적용된다 (목록은 적용, 특정 정책을 묻는 상세는 적용 안 함). 질문 분석 없이 `default_rag`에 상태순 정렬을 넣으면 질문 대상인 마감 정책이 뒤로 밀린다
- 이번 주 준비 (코드 없이)
  - 확인용 질문 세트 초안: 신청 가능 정책이 있는 경우, 마감 정책만 있는 경우, 마감 정책을 지목한 경우, 마감 포함을 요청한 경우
  - 가짜 데이터에 마감 코드 정책 추가 (마감 코드 수정 확인에도 사용)

### 범위 밖
- 신청기간 파싱 예외 4건 (기간 두 개, 더미 날짜, 시작일 > 종료일)은 ETL에서 처리한다: [ETL #2](https://github.com/inha-youthlink/youthlink-data-pipeline/issues/2)
- 상시 코드인데 사업이 이미 끝난 정책(3건)은 이후 필터링·리랭킹 단계에서 다룬다

## 6. debug 모드 (평가 서버 연동)

RAG 평가 서버(RAGAS)가 `POST /internal/pipeline?debug=true`로 채점한다. 기존 키의 이름과 형식은 바꾸지 않는다.

| 요청 | `trace`에 포함되는 키 |
|---|---|
| 기본 | `latency_ms`, `tokens`, `chat_model`, `retriever`, `top_k`, `prompt_version`, `embedding_model` |
| `?debug=true` | 위 키 + `contexts`, `retrieved_chunks` |

- `contexts`: LLM에 넘긴 정책별 근거 블록 (`list[str]`), `[근거]`에 넣은 순서 그대로. 정책이 없으면 `[]`
- `retrieved_chunks`: 5주차 형식 + `content`(청크 본문)
- 기본 요청에서는 `retrieved_chunks`가 빠진다 (백엔드는 아직 사용하지 않음, 평가는 항상 debug로 호출)

### 결정
| 주제 | 결정 | 이유 |
|---|---|---|
| `contexts` | LLM에 넘긴 근거 블록을 그대로 전달 | 평가 쪽이 근거 템플릿을 복제하면 프롬프트 버전이 바뀔 때마다 어긋남 |
| debug 전달 방식 | 쿼리 파라미터 | 평가 서버 요청 형식. `PipelineInput` 계약을 바꾸지 않음 |
| 노출 범위 | 기본 요청은 API 계층에서 **허용 목록**(가벼운 키 7개)으로 거름 | 근거 원문 같은 내부 정보 노출 방지, 응답 크기. 새 키를 추가하고 목록 반영을 잊어도 노출되지 않음 |
| debug 전용 계산 | 지금은 두지 않음. 고도화(리랭킹 등)로 debug 때만 계산할 정보가 생기면 `PipelineContext.debug` 추가 | 지금 debug 정보는 답변 생성 중에 어차피 만들어짐 |

## 7. 채팅 저장

### 테이블 소유
- 채팅 테이블의 DDL과 마이그레이션은 ETL 저장소(`db/migrations/`)에서 관리하고, 변경은 RAG가 ETL에 이슈·PR로 진행한다. 데이터는 RAG가 쓴다
- 이유: 스키마를 한곳(ETL 저장소)에서 보고, 한 DB에 마이그레이션 방식을 하나만 유지한다
- 채팅 데이터는 Spring으로 옮기지 않고 RAG가 계속 저장·조회한다. Spring은 로그인·사용자를 맡고 프론트 요청을 RAG에 전달한다 ([design.md](../design.md) 15절)
  - 대화 상태(현재 정책, 보여준 정책 순서, 질문 분석 결과)는 RAG의 질문 분석 규칙을 위한 정보라, Spring이 대신 들고 다니면 상태가 바뀔 때마다 두 서버를 함께 고쳐야 함
- "한 테이블에 쓰는 서버는 하나" 원칙은 데이터 쓰기 기준이라 그대로 지켜진다

### ERD 변경 요청 ([design.md](../design.md) 16절)
| 요청 | 이유 |
|---|---|
| `chat_room.user_id` (`NOT NULL`, 인덱스) | 사용자별 채팅방 목록, 소유권 확인 |
| `chat_current_policy` 테이블 (`room_id`, `policy_no`, `display_order`) | 후속 질문의 기준 정책 (여러 개 가능) |
| `chat_message.metadata` JSONB | intent, 재작성된 질문, trace 요약 |

### API ([design.md](../design.md) 4-2)
```
POST /api/rooms                     채팅방 생성 (user_id, profile) → room_id
GET  /api/rooms?user_id=...         사용자의 채팅방 목록
GET  /api/rooms/{room_id}/messages  대화 기록 조회
POST /api/rooms/{room_id}/messages  질문 전송 (user_id, question, action)
```

### 처리 흐름
```
POST /api/rooms/{room_id}/messages
  → api/rooms.py                  요청 검증
  → services/chat_service.py
      1. 사용자-채팅방 소유 확인 (다르면 404)        chat_repository
      2. 프로필, 최근 대화, 현재 정책 목록 조회        chat_repository
      3. PipelineInput 구성 → run_pipeline()       5주차 흐름 + 대화 기록
      4. 메시지, metadata, message_policy_ref 저장  chat_repository
  → 응답 (answer, sources 등)
```
- `POST /internal/pipeline`은 그대로 유지한다 (저장 없음, 평가·디버깅용)

### 구현 전에 정할 것
- ~~현재 정책 저장 형태~~ → 목록, `chat_current_policy` 테이블로 확정 (복합 질문·비교 대비)
- 파이프라인에 넘길 최근 대화 턴 수와 `PipelineInput` 필드 (기본값 있는 선택 필드로 추가)
- 질문 전송 응답 형식과 `/internal/pipeline` 응답의 관계

## 9. 확인 환경

- ETL 청킹·임베딩이 완료되어(10-11), 로컬 DB를 ETL 덤프로 새로 구성한다. 덤프를 받기 전까지는 5주차 가짜 데이터(정책 25개)로 확인한다

- 청크 구조가 바뀌어(정책당 최대 4개) 검색 양상이 5주차와 다르다. 실제 데이터 재평가는 7주차에 한다

## 11. 7주차 미리보기

| 순서 | 작업 | 내용 |
|---|---|---|
| 1 | 질문 분석 | intent 분류(LLM 기반 쿼리 라우팅), 질문 재작성, 정책 지목. 출력 스키마에 신청 상태 관련 신호 포함 ("지금 신청 가능한 것만", "마감된 것도") |
| 2 | 신청 상태 우선순위 | [design.md](../design.md) 10-4의 "정할 것" 확정 (상태 순서, 질문 유형별 적용, 관련성 기준, 마감 정책 범위). 신청 기간이 두 개인 정책 판정 (`policy_application_period`, ETL 006) |
| 3 | 1차 필터링 | 첫 조건은 신청 상태. `policy_ids`로 검색 범위 제한 |
| 4 | 핸들러 확장 | 범위 밖 → 정책 상세 → 정책 목록. 핸들러마다 유형별 답변 명세 먼저 ([design.md](../design.md) 12-1). 근거 중복 정리 (`APPLICATION` 청크와 `[신청 방법]`·`[제출 서류]`) |
| 5 | 현재 정책 상태 | 후속 질문의 기준 정책 목록, 정책 지목 ("두 번째 거") |
| 6 | 실제 데이터 재평가 | 5주차 질문 세트, 평가 서버 연동. 청크 구조 변경(ETL 005) 반영 |

- 질문 분석은 intent만 출력하고, 핸들러 선택은 코드가 한다. 핸들러의 차이는 검색 기법이 아니라 무엇을, 어디서, 어떤 범위로 찾는지다
- 1차 필터링은 6주차에 "지역이 빠지면 효과가 작다"는 이유로 미뤘으나, 신청 상태를 첫 조건으로 두면 지역 없이도 의미가 있다. 상태는 코드로 정확히 판정되고 ETL 답변을 기다리지 않아도 된다. 신청 상태 우선순위와 구현 방식(`policy_ids`)이 같아 함께 만든다
- 대기: 지역 코드 반영 (ETL #3 종료 후, `v_policy_region_scope` 활용 검토)
- ~8주차: 자격 확인·비교 핸들러, 관련성 판정
