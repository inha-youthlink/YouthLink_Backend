> 목표: **질문에 맞는 정책을 정확히 찾고, 질문 종류에 맞게 답하는 챗봇**
> 설계 기준 문서: [design.md](../design.md). 이 문서의 3·4절은 `design.md` 9절(핸들러)·10-2절(1차 필터링)보다 우선한다. `design.md`는 Spring 연동 전에 정리한다

## 1. 목표

7주차에 대화 맥락(질문 분석, 현재 정책)과 카드 결정을 만들었다 ([week07.md](week07.md) 12절). 실제 데이터로 확인해 보니 대화 흐름보다 **검색이 약점**이었다. "서울 주거 지원 정책 알려줘"의 top-30에 "청년 월세 지원" 같은 핵심 정책이 없었고, "서울"이라는 단어가 주거와 무관한 서울 정책을 끌어왔다.

8주차에는 검색 전에 조건으로 거르는 **1차 필터링**을 먼저 하고, 그다음 질문 종류별 **핸들러**를 나눈다.

**일정**
- RAG는 10-24(토) 밤에 마감하고, 10-25(일)부터 Spring을 시작한다
- 마감 전에 끝내지 못한 항목은 8절 "나중"으로 넘긴다

**성과 기준**
- "서울 주거 지원 정책 알려줘"에 서울·전국 주거 정책이 카드로 나온다 (7주차: 2개, 핵심 정책 누락)
- 질문에 지역이 없으면 프로필 지역 정책만 나온다 (7주차: 서울 사용자에게 경북·부산 정책)
- 인사·범위 밖 질문에 검색하지 않는다
- 지목한 정책의 상세 질문은 검색 없이 그 정책으로 답한다

## 3. 핸들러 구조 (결정)

**원칙: 흐름(근거를 모으는 방법)이 다를 때만 핸들러를 나눈다. 확실하면 전용 핸들러, 판단이 안 서면 되묻기.**

| 단계 | 역할 |
|---|---|
| 라우터 (`runner`) | 질문 분석 결과로 핸들러 **하나**를 고른다 |
| 핸들러 | 정해진 조립법대로 부품을 부르고, 근거와 카드 후보만 모은다 |
| 부품 | 검색(1차 필터 + 벡터), 후보 선택, 근거 만들기 등. 여러 핸들러가 함께 쓴다 |
| 답변 생성 | 공통 함수 하나. 핸들러가 넘긴 답변 종류로 **프롬프트 조각**을 조립해 한 번 호출 |

| 핸들러 | 받는 질문 | 근거 | 답변 조각 |
|---|---|---|---|
| 검색 | 목록·찾기. 자격 확인·비교·복합 질문(전용 처리 전까지). 분석 실패 (분석 조건 없이) | 1차 필터 → 벡터 검색 → 후보 5개 → 청크 전체 | 추천 (최대 3개) |
| 상세 | `policy_detail` + 지목한 정책이 확인됨 | 지목한 정책 (`policy_ids`, 검색 없음) | 상세 (물은 내용, 신청 방법 안내) |
| 짧은 답변 | 인사, 서비스 질문, 분명한 범위 밖 | 없음 | 짧은 답변 |
| **되묻기 (기본)** | `unclear`, 판단이 안 서는 모든 경우 | 없음 | 되묻기 (현재 정책이나 질문 예시 + 범위 안내) |
| 자격 확인 v1 (시간이 되면) | `eligibility` + 지목한 정책 | 상세와 같음 + 조건별 판정 | 자격 확인 |

- 라우터 규칙: 하위 질문이 1개이고 위 조건에 확실히 맞으면 전용 핸들러. 하위 질문 2개 이상과 분석 실패는 검색. 그 외 판단이 안 서면 되묻기
- 되묻기를 기본으로 하는 이유: 기본까지 오는 질문은 대부분 "정책 관련인데 애매한 질문"이다. 짧은 답변("정책 안내만 가능")이 받으면 정책 질문에 범위 밖이라고 답해 대화가 끊긴다. 되묻기는 틀려도 한 번 더 주고받으면 바로잡힌다
- 되묻기로 보내지 않는 것: 분석 실패(시스템 실패를 사용자에게 넘기지 않음), 분명하지만 전용 처리가 없는 질문
- RAG 없이 LLM이 바로 답하는 범용 핸들러는 두지 않는다. 예상하지 못한 정책 질문에서 일반 지식으로 지어낼 위험이 가장 크다
- 정책 목록(SQL 조회) 핸들러는 두지 않는다. 목록 질문도 주제("월세 지원")가 자유 표현이라 "필터(SQL) → 의미 검색"으로 검색 핸들러가 처리한다
- 핸들러끼리는 서로 호출하지 않는다. 같은 일은 부품으로 공유한다 (LlamaIndex의 라우터 + QueryEngine, Haystack의 라우터 + 파이프라인과 같은 형태)

## 4. 1차 필터링 (결정)

**원칙: 질문에 명시된 것 > 프로필 > 없음. 프로필과 어긋나면 숨기지 않고 알린다.**
- 신뢰도는 사용자가 물은 것에 사실대로 답하는 것이다. 프로필로만 강제하면 서울 사용자가 "인천 창업 지원"을 물을 때 인천 정책이 전부 빠진다
- 질문 지역·나이가 프로필과 다르면 답변에 자격 경고를 붙인다

| 조건 | 질문에 명시 | 질문에 없음 | 강도 |
|---|---|---|---|
| 지역 | 질문 지역 + 전국 | 프로필 지역 + 전국 | 강제 |
| 나이 | 질문 나이 ("동생이 22살") | 프로필 나이 | 강제 (나이 제한 없는 정책 포함). 공고별 예외가 많으면 참고로 낮춤 |
| 코드 조건 (취업 상태, 학력, 전공, 혼인, 특화 대상) | (나중, `analyze_v3`) | 프로필 코드 | 강제. 확실히 안 맞을 때만 제외 |
| 소득 | (나중) | 프로필 연소득 | 강제. 숫자 상한을 확실히 넘을 때만 제외 |
| 마감 여부 | "지금 신청 가능한" → 제외 / "마감된 것도" → 포함 | 정렬만 (마감은 뒤로) | 명시되면 강제 |
| 분야 | "주거 정책" | — | 참고만 (정책 쪽 분류가 엇갈림: 창업자 월세 지원이 일자리·창업 분류) |

- **강제 필터는 결과가 적어도 풀지 않는다.** 조건에 따라 동작이 바뀌면 오히려 신뢰도가 떨어진다. 결과가 없으면 한 문장으로 안내한다: "프로필 조건에 맞는 관련 정책을 찾지 못했어요. 다른 표현으로 물어보시거나, 조건과 관계없이 찾아보고 싶으시면 말씀해 주세요."
- 분석이 실패하면 질문 조건을 모르므로 프로필 조건도 참고로 낮춘다 ("인천" 질문에 서울로 강제하는 사고 방지)
- 판정 함수 하나가 조건마다 ✓ / ✗ / ?를 돌려준다. 1차 필터링은 ✗만 제외하고, 자격 확인은 셋 다 설명한다
- 코드 조건: 프로필 코드가 있고, 정책 목록이 "제한없음"·"기타"가 아니며, 목록에 없을 때만 ✗. 실제 데이터에서 재직자 기준 628개(18%), 미취업자 366개(10%), 대학 졸업 297개(8%)가 제외된다
- 소득: 숫자 기준은 46건뿐(무관 3,063, 문장 기준 432). 단위는 대부분 만 원. **상한만 쓰고 하한은 쓰지 않는다** (부부 합산 기준이어도 내 소득만으로 상한을 넘으면 확실히 ✗, 하한은 합산이면 넘을 수 있음). 상한 0이나 단위가 다른 값은 판정하지 않고 통과
- 필터와 검색은 공통 부품(`search_policies`)으로 만들고, 결과는 `Retriever.retrieve`의 `policy_ids`로 넘긴다

**채팅방 프로필은 계속 수정할 수 없다.** 다른 지역·나이는 질문에 말하면 된다. 한 채팅방 안에서 답변 기준이 같아야 기록을 믿을 수 있다.

## 5. 카드 정보

날짜만 주던 카드는 상시 모집, 마감 코드(조기 종료), 정보 없음을 구분할 수 없고, 프론트가 상태를 다시 계산해야 했다.

- `PolicyItem`에 선택 필드 추가: `application_status`(`OPEN`/`ALWAYS_OPEN`/`UPCOMING`/`CLOSED`/`UNKNOWN`, 본문과 같은 함수로 계산), `supervising_org_name`
- 기록 조회의 카드도 조회 시점 기준으로 상태를 계산한다. DB 변경 없음
- 프론트: 날짜는 `OPEN`·`UPCOMING`일 때만 표시. `application_url`은 절반 이상이 홈페이지 첫 화면이라 버튼 문구는 "관련 사이트"처럼 중립적으로
- 신청 방법을 물으면: 있으면 안내하고, 없거나 실질 정보가 없으면("해당 없음", "별도 문의") "공고에 나와 있지 않다". 어느 경우든 정책 이름, 담당 기관, 관련 링크를 붙여 다음 행동을 안내한다 (`generate_v3`)
- 카드 링크 필드(`link_url`)는 넣지 않는다. 직접 열어 본 링크 3개 중 2개가 오류, 1개가 검색 화면으로 이동해 URL 모양으로 신뢰도를 판단할 수 없음을 확인했다. 응답 필드는 되돌리기 어려워 ETL 보강 이후에 정한다

| 순서 | PR | 최소 완료 기준 |
|---|---|---|
| 1 | 카드 정보 | `application_status`, `supervising_org_name`, 기록 복원, 근거에 참고 링크·담당 기관, 신청 방법 안내 규칙 |
| 2 | 지역 (#10) | 질문 지역 추출, 지역 필터(공통 검색 부품), 프로필 지역을 답변 생성에 전달, 자격 경고, 카드 지역 표시, `tests/sql/` 갱신 |
| 3 | 1차 필터링 (#13) | 판정 함수(✓/✗/?), 나이·코드·소득 상한·마감 여부, 결과 없음 안내 |
| 4 | 신청 상태 우선순위 | 상태 정렬이 관련도를 무시하는 문제 해결 ("관련도가 비슷할 때만 상태 우선" 등). 1차 필터링 뒤의 후보로 실제 질문들을 재서 기준값 결정. 카드 정보 PR의 "확실한 1위 유지"(점수 차 0.05)와 "정보 없음 > 마감" 순서도 다시 봄 |
| 5 | 핸들러 | 상세, 짧은 답변, 되묻기, 검색 분리, 라우터 규칙, 근거 모으기와 답변 생성 분리, 프롬프트 조각 |
| 6 | 자격 확인 v1 (시간이 되면) | 상세 근거 + 판정 결과, 자격 확인 조각. 소득 문장 기준은 LLM 설명 |

- 모두 실제 데이터(`youthlink_real`)로 확인한다. 규칙이 데이터 분포에 달려 있다
- 2·3번에서 필터와 검색을 부품으로 만들어 두어야 5번과 나중의 목록 핸들러가 얇아진다
- 4번을 필터링 뒤에 두는 이유: 필터로 후보 범위가 바뀌면 우선순위 기준을 다시 재야 하므로
