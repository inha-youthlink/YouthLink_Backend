## 3. 결정

**추천 에이전트 방식**
| 결정 | 내용 | 이유 |
|---|---|---|
| 에이전트형 | LLM이 도구(정책 검색·정책 조회)를 골라 부르고, 결과를 보고 다음 질문·선택지·카드를 정함. 도구 호출은 턴당 최대 3회, 넘으면 도구 없이 답하게 강제 | 채팅(라우팅형)은 정확하지만 질문 모양이 정해져 경직됨. 추천은 정확도도 중요하지만 **유연성이 더 중요**: 선택지에 없는 답("월세보다 생활비가 부족해요"), 방향 전환, 후보 수에 따라 질문을 건너뛰기 |
| 첫 질문만 고정 | 인사 + 분야 5개 칩(+ 프론트의 "직접 입력"). LLM 없이 바로 뜸 | 처음은 누구에게나 같은 질문이라 LLM이 필요 없음. 패널이 바로 열림 |
| 그 뒤는 에이전트에 | 질문 리스트를 고정하지 않고, 지시문에 "분야별 질문 가이드"만 둠 (후보가 많을 때만 묻고, 5개 이하면 바로 추천) | 고정 리스트는 프로필마다 후보 수가 크게 달라 쓸모없는 질문이 생기고(후보 3개인데 세부를 물음), "직접 입력" 경로와 갈라짐. 가이드로 일관성은 지킴 |
| 프로필은 코드가 강제 | 검색 도구 안에서 채팅과 같은 1차 필터를 항상 적용. 에이전트가 끄거나 바꿀 수 없음. 프로필 항목은 다시 묻지 않음 | 유연성은 LLM에, 지켜야 할 선은 코드에 (채팅의 "LLM은 해석, 코드는 안전 규칙"과 같은 나눔) |
| 고른 분야는 강제하지 않음 | 분야는 출발점. 사용자가 바꾸면 따라감 | 묶어 두면 유연성이 사라짐 |
| 카드 검증 | 카드는 이번 대화에서 도구가 실제로 돌려준 정책만, 최대 5개 | 지어낸 정책이 카드에 오르지 않음 |
| 카드 5개 | 10개로 늘리지 않음. 더 보고 싶으면 "더 보여줘"(다른 5개) 또는 프론트의 "이 분야 정책 더 보기"(채팅방 안 정책 검색) | 좁혀 주는 것이 역할. 카드마다 추천 이유를 써서 10개면 턴당 1~3초 늘어남. 목업 열 높이 |
| 시작 카드 | 분야를 고르기 전부터 프로필 기준 5개 (추천 정책 API와 같은 필터·순서, 최근 채팅 분야로 좁히기는 뺌). `reason`이 `null`이라 프론트가 소제목으로 구분 | 무엇을 물을지 모르는 사용자에게 실제 정책이 분야를 고르는 실마리가 됨. 빈 열을 피함 |
| 프로필과 다른 조건 | 다른 지역·나이를 말하면 채팅방 프로필 기준이라고 안내하고 새 채팅방을 권함 | 채팅의 "지역 다르면 되묻기"와 같은 취지 |

**저장과 API**
| 결정 | 내용 | 이유 |
|---|---|---|
| 새 테이블 2개 | `chat_agent_message`(턴, 메타데이터에 도구 호출·본 정책), `chat_agent_policy_ref`(턴별 카드·추천 이유). 쓰는 곳은 `agent_repository` 하나 | `chat_message`는 대화 기록·요약·추천 정책·화면이 모두 읽어 섞이면 전부 영향 받음 |
| 닫을 때까지 이어 감 | 대화 길이 상한 없음, 다시 열면 이어 감, "새로 시작"으로 지움. 에이전트 입력에는 최근 대화만 | 사용자가 원할 때까지 좁혀 갈 수 있게. 입력 길이는 따로 묶음 |
| 끝에서 함께 저장 | 답변이 다 만들어지면 사용자 메시지·답변·카드를 한 번에 저장. 실패하면 저장하지 않음 → 같은 글자로 다시 보내면 됨 (`clientMessageId` 없음) | 채팅의 멱등 처리보다 단순함. 저장 직후 끊기는 경우만 프론트가 `GET`으로 확인 |
| 글자 스트리밍 안 함 | SSE `progress`(찾는 중) → `cards` → `message` → `done` | 답변이 질문·선택지·카드가 묶인 하나의 결과(구조화 출력)라서. 기다림은 `progress`로 보여 줌 |
| 동시 실행은 따로 셈 | 같은 방에서 에이전트 답변 중이면 `409`, 채팅과는 별개 | 패널과 채팅을 동시에 쓸 수 있게 |
| 채팅으로 넘기기 | `PUT …/current-policy`: 채팅방의 현재 정책을 그 정책으로 교체. 채팅방 안 정책 상세의 "채팅에서 물어보기" 보조 버튼에서만. 프론트는 placeholder와 "이야기 중" 표시만, 글자 자동 입력·전송 안 함 | 분석이 이미 "화면 밖 현재 정책"(`C1`)과 "이름 없는 질문은 현재 정책" 규칙을 가짐. 연결이 글자에 묶이지 않고, 대화 기록에 가짜 문장이 안 섞이고, 클릭만으로 LLM 비용이 없음. 에이전트와 별개의 일반 API라 다른 화면에서도 쓸 수 있음 |

**채팅의 범용 핸들러 (이후 검토, 결정 아님)**
- 11주차의 `local_only`·복합·범용 핸들러는 사실상 "에이전트가 자연스럽게 하는 일을 핸들러로 하나씩 다시 만드는 일"이다. 라우팅형은 질문 모양을 다 열거할 수 있다는 가정 위에 있고, 그 비용을 치르는 중
- 그렇다고 채팅을 갈아엎지 않는다. 시연이 가깝고, 분명한 질문(상세·비교·되묻기·범위 밖)은 지금 라우터가 빠르고 확실하며 평가(라우팅 혼동 행렬)도 깔끔함
- 방향(안): 추천 에이전트를 완성해 보고 괜찮으면 라우터 **마지막 줄("그 외 → 검색 → 추천")만 에이전트 경로로** 바꾸는 하이브리드. 복합·범용 핸들러를 따로 설계하기 전에 이 경로로 받을 수 있는지 먼저 봄
- 그래서 이번 구현은 도구·루프(공용)와 추천 패널 전용 부분(지시문·출력 모양)을 나누고, trace를 채팅 형식에 맞춤

**하지 않기로 한 것**
| 안 | 이유 |
|---|---|
| 질문 분기표를 미리 다 만들기 | 경우의 수가 늘고, 데이터가 바뀌면 0건 선택지가 생김. 자유 입력에 대응 못 함 |
| 턴마다 검색 1번으로 고정한 2단계 | 게이트웨이가 도구 호출을 지원하고(5절) 검색 1번이면 속도가 같아, 필요할 때만 더 부르는 루프로 감 |
| SQL을 직접 쓰는 넓은 도구 | 프로필 필터를 우회할 수 있음 |
| 에이전트 턴을 `chat_message`에 저장 | 채팅 대화 기록·요약·추천 정책에 섞임 |
| "채팅에서 물어보기"에서 질문 자동 입력·전송 | 지운 글자에 연결이 끊김, 방금 본 상세를 다시 요약하는 중복 답변, 비용 |
