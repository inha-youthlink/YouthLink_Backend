# 11주차 작업 기록 (2026-11-10 ~ 11-15)

> 목표: **중간시연 뒤 프론트 협업 기능(채팅방 삭제, 신청 가이드 PDF)을 끝내고, 다음 핸들러(범용·복합)와 응답 속도의 방향을 잡는다**
> 설계 기준 문서: [design.md](../design.md), 공개 API 계약: [api-contract.md](../api-contract.md) v1.3. 이 문서에는 11주차의 결정과 근거, 한 일을 남긴다 (12주차에 정리해 씀)

---

## 1. 목표

10주차에 비교 핸들러(PR #53)를 넣고 계약을 v1.1로 정리했다 ([week10.md](week10.md)). 11주차에는 프론트가 요청한 채팅방 삭제와 신청 가이드 PDF를 구현하고, 배포 서버 테스트에서 드러난 질문 유형(지역 정책만, 주관적 기준)을 보고 다음 핸들러의 방향을 정한다. 새 기능이 늘기 전에 응답 속도의 기준을 잰다.

## 3. 결정

**채팅방 삭제 (v1.2)**
| 결정 | 내용 | 이유 |
|---|---|---|
| 완전 삭제 | `DELETE /api/sessions/{sessionId}` → `204`. 메시지·카드·현재 정책을 모두 지움, 되돌릴 수 없음. 스크랩은 사용자 단위라 남음 | 채팅 하위 테이블이 이미 `ON DELETE CASCADE`라 스키마 변경 없음. 숨김 삭제는 시연 범위에서 쓸 곳이 없음 |
| 없거나 남의 방은 `404` | 이미 지운 방도 `404` | 다른 세션 API와 같은 규칙 (존재를 숨김) |
| 생성 중 삭제는 막지 않음 | 답변 저장이 FK 오류로 실패해 그 스트림은 `INTERNAL_ERROR`로 끝남 | 이미 지운 방이라 따로 막을 이유가 없음 |
| 프로필 보기는 새 API 없음 | 세션 응답의 `profile`을 씀 | 이미 있는 값 |

**신청 가이드 PDF (v1.3)**
| 결정 | 내용 | 이유 |
|---|---|---|
| LLM은 나누기만 | LLM 한 번으로 공고 원문을 항목(단계·서류·조건·주의사항·용어)으로 나누고 대화에서 사용자가 직접 말한 사실만 뽑음. 날짜·링크·기관명·기본 자격 조건은 코드가 공고 데이터에서 넣음 | 인쇄해 쓰는 문서라 틀린 값이 들어가면 피해가 큼 |
| 할 일 먼저 | 첫 쪽 "한눈에 보기" → 신청 방법 → 제출 서류 → 확인할 조건 → 주의사항 → 내 상황 → 용어 → 안내 → 부록(서류 원문) | 첫 쪽만 봐도 무엇을 할지 보이게 |
| 동기 생성, 같은 출처 링크 | `POST …/guides` → `201 {policyId, pdfUrl, expiresAt, outsideProfile}`. `pdfUrl`은 `/api/guides/{token}.pdf`, 10분 만료, `X-Client-Id` 없이 열림 | 프론트 mock 형식 그대로. 같은 출처라 프록시를 그대로 탐. 브라우저가 링크로 바로 열어 헤더를 붙일 수 없어 추측할 수 없는 토큰을 열쇠로 |
| 저장하지 않음 | 서버 임시 폴더에 파일, 만료 뒤 정리. 다시 볼 때는 다시 만듦 | PDF에 프로필·대화가 들어가 오래 두지 않음 |
| 프로필 밖 정책도 만듦 | 막지 않고 `outsideProfile: true` + 첫 쪽 경고. 어느 조건이 안 맞는지는 판정하지 않음 | 검색·스크랩으로 연 다른 지역 정책도 가이드가 필요할 수 있음. 자격 판정은 하지 않는 원칙 |
| 요청 제한 | 채팅과 같은 기준(분당·하루 상한) | LLM을 부르는 기능 |
| 버튼 위치 (프론트 제안) | 채팅방 안에서 연 정책 상세 + 빠른 실행 패널(이 채팅방의 카드 중 고름). 채팅방 밖 상세에는 숨김 | 가이드는 정책 하나에 대한 문서이고 세션(프로필·대화)이 필요 |

**다음 핸들러 방향 (11-10, 결정 아닌 안 포함)**
| 결정 | 내용 | 이유 |
|---|---|---|
| 개수 지정 제외 | "5개 알려줘"는 하지 않음 | 필요도가 낮고 다른 핸들러가 더 급함 |
| 범용 핸들러가 하나는 필요 (안) | 정책 질문이고 뜻은 분명하지만 정해진 모양이 없는 질문(주관적 기준, 최상급, 예상 못 한 요청)을 받는 경로. 필터된 후보 안에서만 답함 | 라우터 마지막 줄("그 외 → 검색 → 추천")이 사실상 범용 경로인데 목록 모양(후보 6개, 3개 소개 형식)으로 굳어 있음. 사용자는 예상 못 한 모양의 질문을 계속 함. 10주차의 "검색 없이 답하는 LLM 핸들러"(하지 않기로 함)와 다른 안: 근거 없이 답하지 않음 |
| 복합 핸들러는 좁게 (안) | 하위 질문 2개 이상이고 되묻기·인사·범위 밖이 섞이지 않을 때만. 하위 질문마다 근거만 모으고(검색 병렬) 답변은 1회. 분석은 독립일 때만 나눔 | 하위 질문마다 기존 핸들러를 통째로 실행하면 카드·답변 규칙 조합이 끝이 없음. 들어가는 조건을 코드가 정해 경계가 분명함 |
| 순서 (안) | 정직성 규칙(답변) → 속도 측정 → `local_only` → 복합 → 범용 | 확실한 것부터, 흐린 것(범용)은 부품이 갖춰진 뒤. 속도는 복합 전에 재야 늘어난 시간을 비교할 기준이 생김 |

- 범용·복합 핸들러는 12주차에 방향을 다시 봄: 추천 에이전트를 먼저 만들고, 채팅 라우터의 마지막 줄을 에이전트 경로로 바꾸는 방안을 검토 ([week12.md](week12.md) 3절)

**최상급·주관적 질문을 지금 경로로** (서울 27세, 각 3회)
| 질문 | 결과 |
|---|---|
| 제일 금액 큰 월세 지원 찾아서 그거 신청 서류도 알려줘 | 대체로 됨 (근거에 문서 전체가 있어 검색 + 상세가 한 번에). 단 후보 6개 중 최대를 "가장 큰"으로 단정, 마감 정책을 고르고 대안 안내 없음 |
| 별로 유명하지는 않지만 혜택이 좋은 정책 추천해줘 | 사실상 실패. 검색어가 일반적인 말이 되어 후보가 아무거나. 공고에 없는 "잘 알려지지 않은"을 사실처럼 말함 |
| 지원 금액이 제일 큰 주거 정책 알려줘 | 불안정. 실행마다 후보가 바뀜, 대출(최대 4억)을 "지원 금액이 가장 큰"으로 고름 |

- 공통 문제 1 **정직성**: 후보 안 최대를 전체 최대처럼 말함, 확인할 수 없는 기준을 사실처럼 말함, 대출과 지원금을 섞음 → 답변 규칙으로 고칠 수 있음 (후보를 넓히지 않아도)
- 공통 문제 2 **후보 폭**: "혜택 좋은" 같은 기준은 지금 검색이 후보에 반영하지 못함 → 범용 경로가 필요한 곳

**신청 가이드 실제 확인** (11-14, 로컬, 대화 3턴, 정책 3개)
- 4~10초. 단계·조건이 원문에서만 나옴, 대화 사항에 정책 조건이 섞이지 않음, 신청 방법·서류가 없는 정책은 문의처 안내
- 1차에서 고친 것: 대안 방법(온라인 ①/②)을 순서 단계로 나눔 → 한 단계로, 조건에 지원 금액이 섞임 → 프롬프트에서 제외, 추가 자격 원문의 잘린 줄 → 기본 조건 줄만 분리

## 5. 응답 속도 1단계 측정 (11-14)

로컬 서버, 서울 강서구 27세, 시나리오 5개(질문 13개) × 2회. 클라이언트(SSE) 시간 + 답변 trace `latency_ms`·`tokens`.

| 유형 | n | 첫 글자 | 분석 | DB·검색 | 생성 요청→첫 이벤트 | 첫 이벤트→첫 글자 (추론) | 전체 |
|---|---|---|---|---|---|---|---|
| 추천 | 10 | 4.1 | 1.2 | 0.6 | 0.6 | 1.5 | 5.2 |
| 상세 | 4 | 3.2 | 1.3 | 0.4 | 0.5 | 0.7 | 3.7 |
| 비교 | 4 | 6.6 | 2.5 | 0.7 | 0.7 | 2.8 | 9.5 |
| 되묻기 | 6 | 2.3 | 1.7 | 0.0 | - | - | 2.3 |
| 짧은 답 | 2 | 2.2 | 1.3 | 0.0 | 0.4 | 0.1 | 2.3 |

(초, 중앙값)

- **첫 글자 지연은 대부분 답변 모델의 추론**: 요청→첫 이벤트 0.5~0.7초, 그 뒤 추론 토큰 100~500개에 0.7~4.5초. 추론 `low`는 정확도 때문에 쓰지 않기로 해서 손대지 않음
- 분석은 보통 1.1~1.5초, 모델이 추론하면 2~6초 (26개 중 6개, 비교·되묻기에 몰림)
- **이어지는 턴마다 파이프라인 전 약 0.37초**: 대화 기록 조회가 카드 정책마다 지역 표시까지 계산함 (대화 기록에는 번호·이름만 필요)
- **지역 표시 조회가 정책 수와 관계없이 약 0.35초**: 범위 View를 씀. 검색·상세·비교의 정책 조회 시간이 거의 이것
- 프롬프트 캐싱: 입력 전체가 같을 때만 맞고 앞부분만 같은 경우는 0. 게이트웨이에서 앞부분 캐싱이 되지 않는 것으로 보여 우리 쪽에서 고칠 것이 없음
- 같은 질문도 시간대별 차이가 커서, 고친 뒤에는 같은 세트를 이어서 돌려 비교

**2단계 후보 (품질과 무관)**: 대화 기록 조회에서 지역 표시 빼기(이어지는 턴 -0.35초), 지역 표시 쿼리를 정책별 해석 View로 다시 쓰기(검색·상세·비교 -0.3초). 12주차에 추천 에이전트를 먼저 하기로 해 미룸. 측정용 trace 항목(첫 이벤트·첫 글자 시각, 캐시·추론 토큰)은 `feature-latency-measure` 브랜치에 보관
