# 9주차 작업 계획 (2026-10-27 ~ 11-01)

> 목표: **프론트가 실제 RAG 답변을 SSE로 받을 수 있는 공개 API**
> 설계 기준 문서: [design.md](../design.md), 공개 API 계약: [api-contract.md](../api-contract.md) v0.5. 이 문서에는 9주차의 결정과 근거, 작업 순서를 남긴다

---

## 1. 목표

8주차에 공개 API의 세션 4개와 채팅 SSE 뼈대(#38), 배포 준비(#39)를 만들었다 ([week08.md](week08.md) 10절). 9주차에는 뼈대 자리에 실제 RAG를 연결하고(공개 API 1-2), 이어서 공개 API의 나머지와 핸들러 추가까지 이 저장소에서 할 수 있는 일을 순서대로 진행한다.

**일정**
- 프론트 첫 실연동: 10주차 1일 (11-03). 그 전에 공개 API 1-2를 끝내는 것이 목표
- 중간시연: 11주차 (질문 이해 + 기본 분기 + 근거 기반 답변)
- 끝내지 못한 항목은 10주차로 넘긴다

## 2. 상황 (10-29)

| 대상 | 상황 |
|---|---|
| 평가 서버 | 8주차 변경 공유 내용(평가 trace 키, `/internal` 키 등)이 모두 반영됐다고 회신받음 |
| 프론트 | 계약 회신 없음. 백엔드 답변(v0.4)대로 갈 가능성이 높음. 실서버 SSE 확인은 아직 못 함 |
| 인프라 | 서버 구축 중, 아직 안 뜸 (R1 기한 10-27 지남) |
| ETL | 공개 API용 채팅 테이블 마이그레이션 필요 (4절) |

- 프론트·평가 서버·인프라는 한 사람이 맡고 있어, 전달 사항은 묶어서 보낸다
- 막혀 있는 것은 서버 배포뿐이다. 그 밖의 일은 이 저장소에서 먼저 진행한다

**로컬 연동 확인 (10-29)**: 프론트 개발 서버(Vite 프록시)를 로컬 백엔드 뼈대에 붙여 확인했다
- 됨: 세션 생성·조회, 프록시를 거친 SSE(`check_sse.py` 통과), 화면에서 token 스트리밍 → 카드 → `done`
- 프론트 카드 검사가 v0.3 형식(`category`·`region` 필수)이라 뼈대 카드에서 오류가 났다 → 뼈대 카드에 v0.3 필드를 임시로 함께 보내 `done`까지 확인
- 중지 버튼을 누르면 프론트가 메시지 이력을 다시 받는데, 뼈대는 저장하지 않아 대화가 사라진다 (공개 API 1-2에서 질문을 저장한 뒤 다시 확인)
- 로컬로 확인할 수 없는 것: Vercel rewrites, Nginx 버퍼링, AWS 유휴 타임아웃. 서버가 뜨면 계약 조건(15초 대기, 90개)으로 다시 확인한다

## 3. 결정

| 결정 | 내용 | 이유 |
|---|---|---|
| 계약 v0.5 잠정본 | 백엔드 제안(1~3절)대로 계약 4절을 정리하고 이 기준으로 먼저 구현. 바뀌는 내용이 있으면 추가로 반영 | 프론트 회신을 기다리면 공개 API 1-2가 막힘. 계약이 바뀔 수 있는 부분(enum 변환, 카드 필드)은 서비스 계층 한 곳에 모아 고치기 쉽게 함 |
| 카테고리 (H1) | `JOB`·`HOUSING`·`EDUCATION`·`WELFARE`(금융·복지·문화)·`PARTICIPATION` | 정책 데이터 대분류와 1:1. 데이터에서 금융과 복지가 나뉘지 않음 |
| 카드 `category` | 백엔드가 공개 API 1-2에서 채움 | 카드의 분류는 v0.3 계약에 있고 반대하지 않음. B3로 빼는 것은 세션의 `category` |
| 뼈대 유지 | 공개 API 1-2 뒤에도 설정으로 뼈대를 켤 수 있게 남기고, 배포 경로 SSE 확인(R2) 뒤 삭제 | 실제 답변은 10~20초라 90초 스트림 확인을 대신하지 못함 |
| 과도기 호환 | 프론트가 바뀔 때까지 v0.3 형식(시도 enum, 세션 `category`, 카드 `region`)도 함께 받거나 보냄 (계약 4.6) | 첫 실연동 때 프론트는 v0.3 형식일 가능성이 큼. 지역을 5자리 코드로만 받으면 세션 생성부터 실패 |
| ETL 마이그레이션 하나로 | 공개 API 1-2의 `client_message_id`와 공개 API 2의 스크랩 테이블을 한 번에 | ETL 담당과 맞추는 일(머지, DB 적용)이 한 번. 스크랩 계약이 단순해 지금 정해도 위험이 작음 |
| 정책 검색 정렬 | 진행 중 → 예정 → 상시 → 정보 없음 → 마감 (계약 v0.7) | 곧 신청할 수 있는 정책이 상시 정책에 밀려 뒤로 가지 않게 |
| 정책 검색 방식 | SQL(`ILIKE`)로 검색하고 정렬·페이지도 SQL. 1차 필터의 조건 조립을 함께 씀 | 계약의 정렬·페이지 규칙을 벡터 검색으로는 지키기 어려움. 지역 범위가 채팅 추천과 같아짐 |
| 지역 목록 | 시도 → 시군구 두 단계, 구가 있는 시는 시 코드, 시도 순서는 서버가 정함 (서울 → 경기 → 인천 → 행정 표준 순서) | 프로필 저장값·1차 필터 단위와 같음. 새 시도 코드(전남광주 12, 강원 51, 전북 52) 순서로는 화면이 어색함 |
| 정책 상세 문장 | 자격은 서버가 1차 필터와 같은 값으로 조립, 빈 칸은 확인할 곳 안내(기관 문의 먼저, 링크는 참고) | 화면의 자격과 추천에서 거른 기준이 어긋나지 않음. 링크의 절반 이상이 기관 홈페이지 첫 화면 |
| 복합 질문은 뒤로 | 핸들러 추가는 개수 지정 → 비교까지 | 복합 질문은 라우터 확장, 병렬 실행이 필요하고 카드·멱등·스트리밍과 엮임. 중간시연 목표에 없어도 됨 |

## 4. ETL 마이그레이션 (공개 API 1-2 시작 때)

| 변경 | 용도 |
|---|---|
| `chat_message.client_message_id` + `UNIQUE(room_id, client_message_id)` | 채팅 멱등 처리 (계약 R6, 세션 단위) |
| 스크랩 테이블 (예: `client_id`, `policy_no` FK, `created_at`, `UNIQUE(client_id, policy_no)`) | 스크랩 3개 API (계약 v0.3 §4.5) |

- 넣지 않는 것: 세션 `category` (B3로 필요 없음), 신청 방법·링크 보강 (스키마가 아니라 데이터 작업)
- 테스트 스키마 복사본 `tests/sql/schema.sql`도 같이 갱신한다

## 5. 작업 순서

| 순서 | 작업 | 최소 완료 기준 |
|---|---|---|
| 1 | 계약 잠정본 (문서) | 계약 4절, H1, 8주차 체크리스트 정리 |
| 2 | **공개 API 1-2** | 아래 |
| 3 | 공개 API 2 | 정책 검색·상세, 대화 요약, 추천 정책, 지역 목록(B2), 스크랩 |
| 4 | 핸들러 추가 | 개수 지정("5개 알려줘"), 비교. 평가 세트 점수(개발 24/25, 시험 8/10)가 떨어지지 않음 |
| 수시 | 서버 배포 따라가기 | 서버가 뜨면 배포 경로 SSE 확인, 서버 주소를 `front-sync.md`에, `deploy.md` 9절 답 반영 |

**공개 API 1-2 범위**
- ETL 마이그레이션 (4절)
- 프로필: 계약 enum → DB 코드 변환(H2 매핑표, 특히 `OTHER`·`NONE`), 8항목 필수, 나이 15~39, 연소득 만 원 → 원
- 카드·세션: 카드 `category`(H1), 세션 `category` 제거(B3)
- 채팅: 실제 RAG를 스트리밍으로 연결, `policies`를 첫 `token` 직전에(B9), `/internal/pipeline`과 같은 결과
- 멱등 처리(계약 §5.3), 연결이 끊기면 생성 취소(질문은 저장), 스트림 중 실패는 `error` 이벤트
- 과도기 호환, 뼈대는 설정으로 유지
- 끝나면 로컬 연동으로 다시 확인
